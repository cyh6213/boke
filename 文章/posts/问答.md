#### 大家对于Agent提效的需求是什么
我觉得可以按照Agent能力和非Agent能力分为两方面。

非agent能力的第一点就是权限，也是限制的最死的一点<font style="color:#8A8F8D;">，因为现在我们通过Agent提效，我们的大部分操作都是写一个Skill，告诉他要在某一个平台做什么，然后到另一个平台做什么。所以说，其实暂时我们对Agent的能力要求没有那么高，限制的最死的，让我们某一个操作不能够通过Agent提效的，就是权限问题。</font>

然后第二点是平台的Agent可操作性，<font style="color:#8A8F8D;">比如现在做的很好的就是飞书，它的很多能力都可以由Agent来自动的操作。</font>

前面说的两点其实都不太是Agent的开发者需要做的事情，而是公司层面的适配。而对于Agent平台的开发者，我们的主要精力是在Agent能力。<font style="color:#8A8F8D;">每一个Agent它们其实都有不同的侧重点，比如说有的，它就在数据检索方面做了很大的改进，有的则是在办公能力上面，比如说写文件啊，这些上面做了非常大的改进。</font>

总结一下<font style="color:#8A8F8D;">就是权限和平台的可操作性是利用AI提效的硬要求，然后再是Agent能力上面的提高，让在办公环境中利用AI提效能成为现实。</font>

### 项目介绍
自我介绍我已经说过项目目标了，然后我在简单介绍一下这个项目的harness系统和功能实现

在架构上：

<font style="color:rgb(29, 29, 31);">我将系统拆成了三层：</font><font style="color:#8A8F8D;">Planner 负责生成版本化 DAG；Orchestrator 负责校验 DAG，维护节点依赖和 </font>`<font style="color:#8A8F8D;">ready queue</font>`<font style="color:#8A8F8D;">，并行调度满足条件的节点；Agent Runtime 只负责节点内的 ReAct 和工具调用。Harness 则是承载这三层的完整运行环境，统一提供上下文、Workspace、Checkpoint、异常治理、HITL 和 Trace。</font><font style="color:rgb(29, 29, 31);">这个设计主要带来三点价值：</font><font style="color:#8A8F8D;">第一，把模型的不确定推理与系统的确定性控制解耦；第二，统一并行、重试、恢复等执行语义；第三，模型、规划策略和执行引擎可以独立替换和测试。</font>

在功能实现上：

从目标<font style="color:rgb(134, 134, 139);">（减少不必要的人工介入）</font>的角度来看<font style="color:rgb(134, 134, 139);">：设计了规划和执行解耦的架构，由harness系统来推进任务的执行，同时设计设计了审查Loop，让人从审查迭代的循环中脱离，还实现了更加实用的人机交互模式。</font>

从长链路任务<font style="color:rgb(134, 134, 139);">（</font><font style="color:#8A8F8D;">复杂任务怎么跑得完、跑得稳</font><font style="color:rgb(134, 134, 139);">）</font>的角度<font style="color:rgb(134, 134, 139);">：我设计了多Agent交互的模式，上下文组织机制，节点级checkpoint机制，三级异常传播机制，</font><font style="color:#8A8F8D;">共同保证长流程能够顺利跑完全程</font>

从Agent基建的角度<font style="color:#8A8F8D;">：我主要做了五层的Trace记录</font>

从优化的角度看：<font style="color:#8A8F8D;">针对执行速度优化，做了并行执行；针对Plan能力DAG构建正确率做了优化；针对上下文、工具管理做了Token用量方面优化。</font>

其中，还有一些功能在计划当中<font style="color:#8A8F8D;">，比如toolhub工具智能化管理（计划通过Trace调用工具记录，来给planagent提供更多信息来选择tool）、Trace记录实现了，但是还在思考Trace的可视化怎么做，让用户可以更方便对异常溯源；多LLM模型调用（审查agent，planAgent）也暂时还未实现；上下文传递智能化，目前的上下文主要想要实现的目标是在减少工具调用等无关信息的传递，同时尽量传递够用的信息，但是没有根据任务类型的不同，来动态的选择传递信息的量（查天气 vs 复杂任务）</font>

#### <font style="color:rgb(29, 29, 31);">为什么项目叫 GraphHarness？</font>
<font style="color:rgb(134, 134, 139);">这个名字由</font><font style="color:rgb(134, 134, 139);"> </font>**<font style="color:rgb(134, 134, 139);">Graph</font>**<font style="color:rgb(134, 134, 139);"> </font><font style="color:rgb(134, 134, 139);">和</font><font style="color:rgb(134, 134, 139);"> </font>**<font style="color:rgb(134, 134, 139);">Harness</font>**<font style="color:rgb(134, 134, 139);"> </font><font style="color:rgb(134, 134, 139);">两部分组成。</font>

**<font style="color:rgb(134, 134, 139);">Graph</font>**<font style="color:rgb(134, 134, 139);"> </font><font style="color:rgb(134, 134, 139);">来自 Graph Engineering。它不是把所有任务塞进一个 Agent Loop，而是把多个 Agent、工具、审查机制和人工决策点组织成显式的 DAG，由系统根据依赖关系自动推进。加入 HITG 后，就形成了“系统管流程、Agent 管执行、人管关键决策”的协作方式。</font>

**<font style="color:rgb(134, 134, 139);">Harness</font>**<font style="color:rgb(134, 134, 139);"> 不止是确定性调度，而是让这张图可靠运行的完整工程环境。它负责 DAG 校验、依赖解析、并行调度、上下文组装、Checkpoint、异常恢复、HITL 和 Trace，把模型的不确定推理与系统的确定性控制解耦。</font>

<font style="color:rgb(134, 134, 139);">所以可以概括为：</font>**<font style="color:rgb(134, 134, 139);">Graph 定义人和 Agent 如何协作，Harness 保证这套协作能够稳定、可控地运行。</font>**

#### 随着模型能力不断提升，Harness 和 DAG 会不会逐渐失去意义
<font style="color:rgb(134, 134, 139);">我也思考过，随着模型能力不断提升，Harness 和 DAG 会不会逐渐失去意义。</font>

<font style="color:rgb(134, 134, 139);">我的判断是：</font>**<font style="color:rgb(134, 134, 139);">模型能力的提升会压缩 Harness 的范围，但不会消除对确定性调度的需求。</font>**

<font style="color:rgb(134, 134, 139);">在 AI Coding 中已经能看到这个趋势。早期我们需要编写大量 Rules 指导模型如何完成任务；随着模型变强，过多规则反而会限制它，最终留下的往往只有安全边界和必须遵守的约束。DAG 也是一样：如果只是用它告诉模型如何思考、如何完成开放任务，未来确实可能成为能力限制。</font>

<font style="color:rgb(134, 134, 139);">但 DAG 的核心价值不只是帮助模型完成任务，而是</font>**<font style="color:rgb(134, 134, 139);">保证关键流程按照可验证、可追踪、可干预的方式执行</font>**<font style="color:rgb(134, 134, 139);">。在审批、审核、金融等对错误容忍度较低的场景中，模型再聪明，也不能完全依赖概率生成来决定流程。</font>

<font style="color:rgb(134, 134, 139);">因此，我不认为 DAG 会被淘汰。它的应用范围可能会收缩，但会进一步集中到固定流程和高敏感场景中。</font>

#### <font style="color:rgb(29, 29, 31);">项目亮点：异常恢复</font>
我认为项目的一个亮点是<font style="color:#8A8F8D;">，它没有把 Agent 的异常简单处理成统一重试，而是根据异常的影响范围，设计了工具调用级、节点执行级和流程级三层异常治理机制。</font>

**<font style="color:#8A8F8D;">第一层是工具调用级。</font>**<font style="color:#8A8F8D;">对于超时等临时性问题，采用指数退避直接重试，不返回给模型；遇到参数错误则把结构化错误返回给模型修正；遇到鉴权失败和非法操作等不可恢复异常则直接上抛。</font>

**<font style="color:#8A8F8D;">第二层是节点执行级。</font>**<font style="color:#8A8F8D;">如果工具重试耗尽，或者模型出现思路停滞、和结果质量不合格，Harness 会创建新的 NodeAttempt。它会保留已经验证的事实和工具结果，清理错误的 ReAct 历史，再根据失败原因重新组装上下文，进行重试。</font>

**<font style="color:#8A8F8D;">第三层是流程级。</font>**<font style="color:#8A8F8D;">如果节点仍然失败，调度器 会根据预设的 处理策略，选择中断流程、还是使用默认值、进入异常分支，或者人工介入。人工处理后，再从对应的 Checkpoint 恢复，不重新执行未受影响的节点。</font>

<font style="color:#8A8F8D;">这套机制的价值是：</font>**<font style="color:rgb(134, 134, 139);">用尽可能低的成本恢复可恢复异常，同时让不可恢复异常快速失败，使流程能够在明确边界内尽可能继续执行。</font>**

#### <font style="color:rgb(29, 29, 31);">项目难点：分层异常恢复</font>
我认为项目中实现难度最大的是异常恢复。

我先介绍一下我们这里的异常处理机制。

<font style="color:#8A8F8D;">这里设计了三层的异常处理机制，核心原则是：</font>**<font style="color:#8A8F8D;">能够局部恢复，就不扩大故障范围；局部无法解决，再向上冒泡。</font>**

**<font style="color:#8A8F8D;">第一层是工具调用级。</font>**<font style="color:#8A8F8D;">对于超时等临时性问题，采用指数退避直接重试，不返回给模型；遇到参数错误则把结构化错误返回给模型修正；遇到鉴权失败和非法操作等不可恢复异常则直接上抛。</font>

**<font style="color:#8A8F8D;">第二层是节点执行级。</font>**<font style="color:#8A8F8D;">如果工具重试耗尽，或者模型出现思路停滞、和结果质量不合格，Harness 会创建新的 NodeAttempt。它会保留已经验证的事实和工具结果，清理错误的 ReAct 历史，再根据失败原因重新组装上下文，进行重试。</font>

**<font style="color:#8A8F8D;">第三层是流程级。</font>**<font style="color:#8A8F8D;">如果节点仍然失败，调度器 会根据预设的 处理策略，选择中断流程、还是使用默认值、进入异常分支，或者人工介入。人工处理后，再从对应的 Checkpoint 恢复，不重新执行未受影响的节点。</font>

**这里面遇到的难点是在**<font style="color:#8A8F8D;">我们异常处理策略的第二层，</font>**<font style="color:#8A8F8D;">节点重试时，如何重新构建一份既保留有效成果、又不会继承错误思路的上下文。</font>**

<font style="color:rgb(134, 134, 139);">节点级主要有两类问题。输出 Schema 不合格比较容易处理：保留原始证据和待修正结果，注入字段级错误，让新的</font><font style="color:rgb(134, 134, 139);"> </font>`<font style="color:rgb(134, 134, 139);">NodeAttempt</font>`<font style="color:rgb(134, 134, 139);"> </font><font style="color:rgb(134, 134, 139);">定向修改。更难的是模型循环或长期无进展。</font>

<font style="color:rgb(134, 134, 139);">我最初想的是竖切一刀，通过判断旧 ReAct 从哪一步开始走错，保留前面的正确部分、删除后面的错误部分。但是我想不出来怎么做，而且只要保留旧的推理轨迹，就可能让模型继续锚定原来的思路。</font>

<font style="color:rgb(134, 134, 139);">最后我的解决方案是横切一刀，把</font>**<font style="color:rgb(134, 134, 139);">执行成果与推理过程解耦</font>**<font style="color:rgb(134, 134, 139);">：只继承执行结果，不继承原来的 Thought、ReAct 历史。这样既避免从头重复获取信息，也降低了新一轮重试被旧思路误导的风险。</font>



# GraphHarness
### Planner–Orchestrator–Agent Runtime 分层架构
#### harness系统的意义
<font style="color:rgb(29, 29, 31);">我设计 Harness，核心是为了解决一个矛盾：</font>**<font style="color:rgb(29, 29, 31);">模型擅长推理，但不适合管理长链路任务的确定性流程。</font>**

<font style="color:rgb(29, 29, 31);">一个任务除了 Planner 生成 DAG、Agent 执行节点，还涉及 DAG 校验、依赖解析、并行调度、上下文组装、状态持久化、异常恢复、HITL 和 Trace。如果全部交给 Agent，不仅容易漏步骤、重复执行，调度和存储逻辑也会与模型、Prompt 强耦合。</font>

<font style="color:rgb(29, 29, 31);">所以我将系统拆成三层：</font><font style="color:#8A8F8D;">Planner 负责生成版本化 DAG；Orchestrator 负责校验 DAG，维护节点依赖和 </font>`<font style="color:#8A8F8D;">ready queue</font>`<font style="color:#8A8F8D;">，并行调度满足条件的节点；Agent Runtime 只负责节点内的 ReAct 和工具调用。Harness 则是承载这三层的完整运行环境，统一提供上下文、Workspace、Checkpoint、异常治理、HITL 和 Trace。</font>

<font style="color:rgb(29, 29, 31);">这个设计主要带来三点价值：</font><font style="color:#8A8F8D;">第一，把模型的不确定推理与系统的确定性控制解耦；第二，统一并行、重试、恢复等执行语义；第三，模型、规划策略和执行引擎可以独立替换和测试。</font>

<font style="color:rgb(29, 29, 31);">所以 Harness 系统的意义就是给模型加上一套工程‘缰绳’，把 Agent 能力变成可编排、可恢复、可观测、可测试的运行系统。”</font>

### Agent 全链路可观测
#### 设计
我的 Trace 设计主要解决两个问题：**如何完整还原一次 Agent Workflow 的执行过程，以及出现问题后，如何追踪系统的完整处理链。**整体按照“执行粒度、记录模型、关系组织、跨层关联”四个部分展开。

**第一是六级细粒度执行模型。**我把一次执行拆成 Run → Node → NodeAttempt → Round → ToolCall → ToolAttempt。这里不仅记录逻辑任务，还专门引入了 Attempt，用来区分“系统想完成什么”和“为完成它实际尝试了几次”。比如 Agent 只决定查询一次订单，因此只有一个 ToolCall；但底层请求两次超时、第三次成功，就会产生三个 ToolAttempt。这样既能统计 Agent 的工具选择，也能分析底层的请求、重试和错误情况。

**第二是 Span 与 Event 双模型**。Span 记录有明确开始和结束的执行过程，包括耗时、状态和结果，用来构成执行链路的骨架；Event 记录某个时刻发生的关键事实，例如触发重试、权限拒绝、上下文裁剪、分支命中或者进入 HITL。也就是说，Span 负责还原系统执行了什么，Event 负责补充执行过程中发生了什么。

**第三是调用关系与业务语义分离。**我使用 span_id 和 parent_span_id 将六级 Span 组织成调用树，表示谁调用了谁；同时保留 node_id、node_attempt_id、tool_call_id 和 tool_attempt_id 等业务 ID，说明当前记录对应哪个逻辑任务以及哪次物理执行。这样 Trace 的存储结构不会和具体业务语义强耦合，同时又能准确定位业务对象。

**第四是跨层问题处理链关联。**调用树只能表达调用关系，但一次异常可能跨越多个层级，经历工具重试、异常冒泡、节点恢复、降级以及 HITL。因此我增加了 correlation_id，用同一个 ID 关联这次问题涉及的多个 Span 和 Event，完整还原一个问题从发生到最终处置的过程。

所以这套 Trace 最终能够回答两类问题：一次任务具体是怎么执行的，以及某个问题发生之后，系统是怎么一步步处理的。

#### 异常排查
<font style="color:rgb(134, 134, 139);">第一条是按 </font>Span 层级下钻<font style="color:rgb(134, 134, 139);">：先通过 </font>`<font style="color:rgb(134, 134, 139);">run_id</font>`<font style="color:rgb(134, 134, 139);"> 查看完整时间线，定位异常 Node，再进入具体的 NodeAttempt、Round、ToolCall 和 ToolAttempt。这条路径回答的是“问题发生在哪里”。</font>

<font style="color:rgb(134, 134, 139);">第二条是通过 </font>`correlation_id` <font style="color:rgb(134, 134, 139);">还原异常处理过程。因为一次工具超时可能在 Tool Runtime 触发重试，重试耗尽后又升级到 Orchestrator，随后触发降级或者 HITL。这些动作分散在不同 Span，单靠父子关系无法说明它们是在处理同一个问题。因此，第一次需要跨层处理异常时生成一个 </font>`<font style="color:rgb(134, 134, 139);">correlation_id</font>`<font style="color:rgb(134, 134, 139);">，并通过 Trace Context、</font>`<font style="color:rgb(134, 134, 139);">ErrorEnvelope</font>`<font style="color:rgb(134, 134, 139);"> 或消息 Payload 继续传递。当异常恢复或明确终止后，就停止向后续正常执行传播这个 </font>`<font style="color:rgb(134, 134, 139);">correlation_id</font>`<font style="color:rgb(134, 134, 139);">，但已有记录会永久保留。因此，</font>`<font style="color:rgb(134, 134, 139);">parent_span_id</font>`<font style="color:rgb(134, 134, 139);"> 用来回答“调用层级是什么”，</font>`<font style="color:rgb(134, 134, 139);">correlation_id</font>`<font style="color:rgb(134, 134, 139);"> 用来回答“这些分散的动作是否在处理同一个问题”。</font>

### 三级异常治理
#### <font style="color:rgb(29, 29, 31);">三级异常实现</font>
<font style="color:#8A8F8D;">我没有把 Agent 的异常简单处理成统一重试，而是根据异常的影响范围，设计了工具调用级、节点执行级和流程级三层异常治理机制。</font>

**<font style="color:#8A8F8D;">第一层是处理工具故障。</font>**<font style="color:#8A8F8D;">对于超时等临时性问题，采用指数退避直接重试，不返回给模型；遇到参数错误则把结构化错误返回给模型修正；遇到鉴权失败和非法操作等不可恢复异常则直接上抛。这一层主要解决工具调用中的局部、短暂故障，避免一次网络抖动或参数错误直接导致整个节点失败，同时防止无差别重试造成资源浪费或重复副作用。</font>

**<font style="color:#8A8F8D;">第二层是处理节点执行问题。</font>**<font style="color:#8A8F8D;">如果工具重试耗尽，或者模型出现思路停滞、和结果质量不合格，Harness 会创建新的 NodeAttempt。同样的上下文原样重试通常没有意义，所以它会保留已经验证的事实和工具结果，清理错误的 ReAct 历史，再根据失败原因重新组装上下文，进行重试。</font>

**<font style="color:#8A8F8D;">第三层是决定整个流程如何继续。</font>**<font style="color:#8A8F8D;">如果节点仍然失败，调度器 会根据预设的 处理策略，选择中断流程、还是使用默认值、进入异常分支，或者人工介入。人工处理后，再从对应的 Checkpoint 恢复，不重新执行未受影响的节点。这一层解决的是局部恢复已经无法处理时，整个业务流程应该如何继续的问题。它避免单个非关键节点拖垮整条流程，也避免系统为了“跑完”而静默吞掉关键错误。</font>

<font style="color:#8A8F8D;">最后呢就是这套系统搭配了我们的Trace记录系统支持的可视化机制，专门设计了异常id，可以将一次异常引发的三层异常串成完整的问题处理链。</font>

#### **节点重试时，如何重新构建一份既保留有效成果、又不会继承错误思路的上下文**
<font style="color:rgb(134, 134, 139);">节点级主要有两类问题。输出 Schema 不合格比较容易处理：保留原始证据和待修正结果，注入字段级错误，让新的</font><font style="color:rgb(134, 134, 139);"> </font>`<font style="color:rgb(134, 134, 139);">NodeAttempt</font>`<font style="color:rgb(134, 134, 139);"> </font><font style="color:rgb(134, 134, 139);">定向修改。更难的是模型循环或长期无进展。</font>

<font style="color:rgb(134, 134, 139);">我最初想的是竖切一刀，通过判断旧 ReAct 从哪一步开始走错，保留前面的正确部分、删除后面的错误部分。但是我想不出来怎么做，而且只要保留旧的推理轨迹，就可能让模型继续锚定原来的思路。</font>

<font style="color:rgb(134, 134, 139);">最后我的解决方案是横切一刀，把</font>**<font style="color:rgb(134, 134, 139);">执行成果与推理过程解耦</font>**<font style="color:rgb(134, 134, 139);">：只继承执行结果，不继承原来的 Thought、ReAct 历史。这样既避免从头重复获取信息，也降低了新一轮重试被旧思路误导的风险。</font>

### 上下文与产物管理
#### <font style="color:rgb(29, 29, 31);">你是如何设计系统的上下文与产物管理的？</font>
这部分主要思考两个问题<font style="color:rgb(134, 134, 139);">：上游 Agent 的产出以什么形式、存放在哪里；下游 Agent 又应该获取哪些内容。</font>

整个方案经历了三次迭代。

**<font style="color:rgb(134, 134, 139);">1.0 阶段采用全量上下文传递。</font>**<font style="color:rgb(134, 134, 139);">  
</font><font style="color:rgb(134, 134, 139);">最开始，我直接把上游 Agent 的完整执行历史，全部传给下一个节点。但多个节点串联后，信息会不断累积。很快就会占满 Context Window。</font>

**<font style="color:rgb(134, 134, 139);">2.0 阶段改为结构化输出和按需输入。</font>**<font style="color:rgb(134, 134, 139);">  
</font><font style="color:rgb(134, 134, 139);">我首先考虑过把完整历史压缩成摘要，但这既需要额外调用模型，也可能丢失细节。因此，我借鉴 Dynamic Workflow 的思路，在生成 DAG 时为每个节点动态定义输出 Schema。节点完成后，只保存和传递经过 Schema 校验的</font><font style="color:rgb(134, 134, 139);"> </font>`<font style="color:rgb(134, 134, 139);">NodeOutput</font>`<font style="color:rgb(134, 134, 139);">，不再传递完整执行历史。</font>

<font style="color:rgb(134, 134, 139);">输入侧也不再累积整条链路的输出。每个节点默认只接收原始任务、Plan，以及直接依赖节点的结构化输出；其他节点的信息独立存储，Agent 确实需要时再通过 Tool 按需查询。这样，节点间传递的信息量降低到了原始内容的 10%～20%，也基本解决了上下文持续膨胀的问题。</font>

**<font style="color:rgb(134, 134, 139);">3.0 阶段进一步加入 Workspace 和产物版本管理。</font>**<font style="color:rgb(134, 134, 139);">  
</font><font style="color:rgb(134, 134, 139);">2.0 解决了文本上下文的问题，但代码、报表等中间产物仍然分散，难以判断应该使用哪个版本。因此，我设计了统一的</font><font style="color:rgb(134, 134, 139);"> </font>`<font style="color:rgb(134, 134, 139);">Workspace</font>`<font style="color:rgb(134, 134, 139);">，集中管理用户需求、全局约束和各类文件产物。</font>

<font style="color:rgb(134, 134, 139);">Workspace 使用本地 Git 管理版本。每个节点成功后，会把修改提交为一个 commit，并把 </font>`<font style="color:rgb(134, 134, 139);">commit_sha</font>`<font style="color:rgb(134, 134, 139);"> 写入对应的 </font>`<font style="color:rgb(134, 134, 139);">Checkpoint</font>`<font style="color:rgb(134, 134, 139);">。需要回滚时，系统会同时恢复节点状态和对应的文件版本。</font>

<font style="color:rgb(134, 134, 139);">所以，这套方案就是：</font>**<font style="color:rgb(134, 134, 139);">结构化 </font>**`**<font style="color:rgb(134, 134, 139);">NodeOutput</font>**`**<font style="color:rgb(134, 134, 139);"> 负责节点间的信息传递，Workspace + Git + Checkpoint 负责中间产物和版本状态的一致性。</font>**

#### 子节点的输入你是怎么做的？
> 子 Agent 的 Prompt 组织主要解决两个问题：**默认给它哪些信息，以及这些信息按照什么顺序组织。**我的原则是只提供完成当前节点所需的最小完整上下文，同时让稳定约束优先、动态信息靠后、大型产物按需读取。整体分成六层。  
>
> **第一层是 System Prompt，定义稳定规则。**包括 Agent 的职责边界、安全要求、工作原则、工具规则和通用输出要求。这部分最稳定，也最不能被后续内容干扰，所以放在最前面。  
>
> **第二层是 Workflow Context，帮助它理解全局目标。**包括用户原始需求、全局约束、验收标准、当前 Plan 和轻量化 DAG 概览。这里只说明整体流程和依赖关系，不注入其他节点的完整执行历史。  
>
> **第三层是 Node Prompt，明确当前要做什么。**包括节点目标、输入要求、完成条件、Workspace 读写范围、失败处理方式，以及什么时候必须触发 HITL。  
>
> **第四层是 Dependency Context，提供必要的上游信息。**默认只注入直接依赖节点经过 Schema 校验的结构化输出，包括结果、告警、未解决问题和必要的 Artifact 引用，而不是累积所有祖先节点的上下文。  
>
> **第五层是 Tool Context，说明当前可以怎么做。**包括可用工具、权限、预算和调用限制。如果默认上下文不够，Agent 可以通过 `context_query` 和 `context_get` 主动查询其他节点的信息。查询结果必须携带来源节点、文件路径和 `commit_sha`；大型内容只返回引用，需要时再读取，查询不到则明确返回 `context_missing`，不能让模型自行补全。  
>
> **第六层是 Output Contract，约束最终产出。**系统会根据动态 `NodeOutput Schema` 明确必填字段、`ArtifactRef` 格式，以及成功、部分成功和失败的表达方式，保证输出能够被下游节点稳定消费。  
>
> 所以这套设计不是简单地压缩 Prompt，而是建立一条明确的信息链：**先固定行为边界，再说明全局目标，然后聚焦当前任务，提供最小依赖，开放按需查询，最后约束输出。**这样既能保证子 Agent 理解任务，又能避免全量上下文累积造成的 Token 膨胀和注意力干扰。
>

#### 关于并行修改
这里主要是约束并行执行的subagent不能同时修改一个文件，首先是他们一般是生成产物，而不是去修改上游产物，所以正常不会出现同时修改一个文件的情况。

然后我也去考路过使用brach+workTree针对每一个并行分支创建一个版本，但是一方是我觉得有一点复杂，如果有冲突还需要手动解决，另一方面是我看其他的CodingAgent也没有使用，所以我就放弃了。

### Plan 架构与能力优化
#### <font style="color:rgb(29, 29, 31);">为什么拆成两阶段 Plan？</font>
<font style="color:rgb(29, 29, 31);">这个改造不是一开始就设计好的，而是随着 Plan Agent 职责增加逐步演化出来的。</font>

<font style="color:rgb(29, 29, 31);">早期 Plan Agent 只需要生成任务流程，输出内容比较简单，DAG 构建正确率较高。后来我们增加了工具选择、节点输入输出、数据映射、执行约束等能力，单次生成的目标变得过多，plan的质量出现明显下降。</font>

<font style="color:rgb(29, 29, 31);">因此我们设计了两阶段 Plan：</font>

+ <font style="color:rgb(29, 29, 31);">第一阶段：流程规划。只生成任务节点、节点职责和依赖关系，优先保证任务覆盖、拆解粒度和 DAG 拓扑合理。用户也可以在这一阶段调整节点粒度和流程方向。</font>
+ <font style="color:rgb(29, 29, 31);">第二阶段：执行配置。在确认后的 DAG 上，为每个节点补充 Agent、Tools、输入输出 Schema、数据映射和验收条件，使其成为可以直接执行的图。</font>

<font style="color:rgb(29, 29, 31);">所以本质上，这是把一个复杂的联合生成问题，拆成“</font>**<font style="color:rgb(29, 29, 31);">先确定做什么，再确定怎么执行</font>**<font style="color:rgb(29, 29, 31);">”两个约束更明确的问题。改造后，DAG 构建正确率恢复并提升到了 97%。</font>

#### <font style="color:rgb(29, 29, 31);">两级规划+校验</font>
<font style="color:rgb(29, 29, 31);">我们的 Plan 采用两阶段设计，核心思路是：</font>**<font style="color:rgb(29, 29, 31);">先确定做什么，再确定怎么执行，并在每个阶段完成对应校验。</font>**

<font style="color:rgb(29, 29, 31);">第一阶段是</font>**<font style="color:rgb(29, 29, 31);">流程规划</font>**<font style="color:rgb(29, 29, 31);">。Plan Agent 根据用户目标完成任务拆解，生成节点职责、依赖关系和并行结构。此时系统先通过图算法校验 DAG 是否无环、连通、依赖合法，再由 Review Agent 检查任务覆盖、拆解粒度和流程逻辑。校验通过后展示给用户调整，确认后冻结流程拓扑。</font>

<font style="color:rgb(29, 29, 31);">第二阶段是</font>**<font style="color:rgb(29, 29, 31);">执行配置</font>**<font style="color:rgb(29, 29, 31);">。Plan Agent 在已确认的 DAG 上，为各节点补充执行 Agent、Tools、输入来源、输出 Schema、数据映射和验收条件。随后通过 JSON Schema 和执行契约校验，检查格式、工具参数及上下游数据是否匹配；Review Agent 再评估节点任务与执行配置是否一致。</font>

<font style="color:rgb(29, 29, 31);">全部通过后，才交给引擎执行。整体流程是：</font>

**<font style="color:rgb(134, 134, 139);">需求输入 → 流程规划 → 拓扑与语义校验 → 用户校准 → 执行配置 → 格式与契约校验 → 可执行 DAG</font>**

<font style="color:rgb(29, 29, 31);">这样能让错误在产生阶段就被发现，避免错误流程进入配置阶段。</font>

#### <font style="color:rgb(29, 29, 31);">后置校验具体校验什么？DAG正确的标准是什么？</font>
<font style="color:rgb(29, 29, 31);">我们将后置校验分为四层，而且每层使用的工具不同。总体原则是：</font>**<font style="color:rgb(29, 29, 31);">能用确定性代码校验的，就不交给模型。</font>**

1. **<font style="color:rgb(29, 29, 31);">格式校验</font>**<font style="color:rgb(29, 29, 31);">：使用 JSON Schema Validator，检查 JSON 是否可解析、字段是否完整、类型是否正确，确保结果能被引擎和前端消费。</font>
2. **<font style="color:rgb(29, 29, 31);">图结构校验</font>**<font style="color:rgb(29, 29, 31);">：使用确定性图算法检查环、非法节点引用、不可达节点以及异常起止节点，保证 DAG 拓扑合法。</font>
3. **<font style="color:rgb(29, 29, 31);">执行契约校验</font>**<font style="color:rgb(29, 29, 31);">：通过规则程序检查 Tool 是否存在、参数是否符合 Schema，以及节点输入能否由用户输入或上游输出提供，保证图能够实际运行。</font>
4. **<font style="color:rgb(29, 29, 31);">语义逻辑校验</font>**<font style="color:rgb(29, 29, 31);">：这部分难以通过代码约束，因此由独立 Review Agent 对照原始需求，从任务覆盖、拆解粒度、依赖关系和工具匹配四个维度进行评审。</font>

<font style="color:rgb(29, 29, 31);">前面三层发现问题会直接阻断执行；语义层输出结构化问题和修改建议，必要时交由用户确认。这样既利用代码保证确定性，也只让模型处理真正需要语义判断的问题。</font>

### 双层并行调度
#### 并行执行
调度我用 Kahn 拓扑排序。<font style="color:#8A8F8D;">因为节点执行是动态推进的：维护每个节点的剩余依赖数（入度），入度为 0 的进 ready queue，节点进入终态后发事件去减后继入度，减到 0 就入队。这样既能发现环，也天然支持并行和条件分支。</font>

内层是工具级，<font style="color:#8A8F8D;">同一节点内 ReAct 一轮模型一次产出多个互不依赖的 ToolCall，并发执行，有数据依赖的串行。</font>

测评：<font style="color:#8A8F8D;">200 项任务评测里端到端 wall time 比完全串行低 23%，这个数字固定了模型版本、工具延迟和并发参数，是评测环境数字，和图的可并行宽度强相关。</font>

#### 普通的Agent也可以并行执行任务，那我们的差距在哪里？
差距在思维方式上，普通的Agent是在思考哪些任务可以并行执行，而我们的agent是只需思考任务的依赖关系，而我们的算法会根据他输出的DAG图给出并行执行方案，而这个方案就是最大程度的并行，这是规则决定的，而不是模型规划能力决定的

### 人机交互
#### 系统的HITX
我的项目提供了两层的人工介入，包括HITL、HITG。

HITL就是<font style="color:#8A8F8D;">传统的，单个Agent React的过程中，遇到信息不足、准备调用高风险工具时，需要临时向人请求帮助。</font>

<font style="color:rgb(29, 29, 31);">HITG 则是</font><font style="color:#8A8F8D;">把人工介入作为 Graph 中的一类正式任务节点，把人当做一个subagent来调用。它不是临时帮助 Agent，而是在实际场景中，会遇到一些任务是受到权限、安全等各种因素，只能由人来完成的。</font>

<font style="color:rgb(29, 29, 31);">二者的区别主要有两点：</font>

+ <font style="color:rgb(29, 29, 31);">HITG是预先定义好的，我清楚在这个流程中哪里需要人介入；HITL是临时的，是由Agent自己决定发起的。</font>
+ <font style="color:rgb(29, 29, 31);">第二点区别就是，HITG需要完成的任务更加复杂，只做决断。所以我在这里把这个HITG设计为了一个任务节点，把人当做SubAgent一样的调用：让系统根据任务准备好任务背景、上游产物、待决策事项和可选操作，而不是默认人了解全部上下文。人可以通过对应的输入窗口提交审批结果、产物或处理意见；将结果写回 Workflow，再推进后继节点。这个策略带来了很大的提效，因为他将我们人需要完成任务的上下文直接准备好了。</font>

#### <font style="color:rgb(29, 29, 31);">HITG/HITL：人应该扮演什么角色</font>
主要有四方面：

+ 澄清：Agent 不确定用户意图，主动提问
+ 审批：Agent 准备执行某步，等人点头
+ 审核：Agent 产出初稿，人审核修改后再继续
+ 接管：有的任务受限于权限、安全性需要人来完成

#### <font style="color:rgb(29, 29, 31);">HITL怎么实现？</font>
<font style="color:rgb(134, 134, 139);"> HITL 通常实现为 </font>**<font style="color:rgb(134, 134, 139);">执行拦截、状态保存、人工回调、上下文恢复</font>**<font style="color:rgb(134, 134, 139);"> 四步。</font>

<font style="color:rgb(134, 134, 139);">Agent 在 ReAct 循环中准备执行高风险 ToolCall，或者遇到信息不足、低置信度时，就会拦截本轮执行，生成结构化的 </font>`<font style="color:rgb(134, 134, 139);">interrupt</font>`<font style="color:rgb(134, 134, 139);">，包含介入原因、待确认操作、工具参数、上下文摘要和期望的人类输入类型。</font>

<font style="color:rgb(134, 134, 139);">系统随后序列化当前 Agent 状态，以等待人工介入之后恢复，等待期间释放线程和模型资源。</font>

<font style="color:rgb(134, 134, 139);">人通过聊天卡片或 Web 页面提交批准、拒绝、修改或补充信息。服务端校验身份、权限、输入格式，再把人工结果作为新的 信息 加入上下文，恢复 ReAct 循环：批准就执行原 ToolCall，修改就用新参数执行，补充信息就继续推理，拒绝则终止或重新规划。</font>

### Loop与质量门禁
#### 你是如何实现减少人工检查的？
<font style="color:rgb(134, 134, 139);">这里主要是通过 </font>**<font style="color:rgb(134, 134, 139);">Loop Engineering</font>**<font style="color:rgb(134, 134, 139);"> 的思想建立质量门禁。</font>

<font style="color:rgb(134, 134, 139);">在实践中通常有两个问题：第一，完成标准不明确，Agent 不知道什么时候应该结束；第二，即使设置了标准，如果仍由执行 Agent 自己检查自己的结果，它容易受到原有思路影响，无法客观判断是否真正完成。</font>

<font style="color:rgb(134, 134, 139);">所以我做了两件事：</font>**<font style="color:rgb(134, 134, 139);">一是为任务定义明确的完成标准，例如必须交付哪些产物、满足哪些字段和质量要求；二是将生成和验收拆开，引入独立的 Review Agent，而不是让执行 Agent 自我审查。</font>**

<font style="color:rgb(134, 134, 139);">具体实践中，不管是 Plan 侧还是节点侧，我都采用了两层质量门禁。</font>**<font style="color:rgb(134, 134, 139);">首先，优先使用确定性校验</font>**<font style="color:rgb(134, 134, 139);">，通过 JSON Schema、图算法和规则程序检查能够被代码明确判断的问题，例如格式与字段类型、DAG 拓扑与执行契约，以及 Artifact 是否完整。</font>**<font style="color:rgb(134, 134, 139);">在确定性校验通过后，再进行语义校验</font>**<font style="color:rgb(134, 134, 139);">，由独立的 Review Agent 对照原始目标和任务完成标准，判断任务覆盖是否完整、拆解与依赖是否合理、工具是否匹配、结论是否有证据支撑，以及是否存在逻辑矛盾或内容遗漏。</font>

<font style="color:rgb(134, 134, 139);">审查未通过时，Review Agent 会输出结构化的问题和修改建议，由系统自动触发新的 </font>`<font style="color:rgb(134, 134, 139);">NodeAttempt</font>`<font style="color:rgb(134, 134, 139);">；只有当审查通过或者多次审查仍未通过时，才进入 HITG。这样就把大部分人工逐次验收转化成了自动质量门禁。</font>

#### 为什么执行、审查Agent要分离？
因为执行 Agent 的目标是完成任务，如果让他自己审查的话，相当于"自己考自己"；

而审查 Agent 不参与执行，视角独立，并且他有单独的审查Prompt，执行审查任务更专业。此外，我们还要求审查agent必须要输出不通过的原因，我们会将原因反馈给执行agent，让他进行修改。

这种"执行与验收职责分离 +"的组合，比让执行 Agent 自查更可靠。

# 概念
### Harness、Graph、Loop
#### HarnessEngineering
Harness 这个概念本质上是在回答一个问题：为什么同样一个模型，在不同的产品里表现天差地别？答案就是 <font style="color:#8A8F8D;">Agent 等于模型加 Harness，模型提供的是智能，而 Harness 是让这份智能真正落地的系统。</font>

那harness包含哪些内容呢？<font style="color:#8A8F8D;">你想要 Agent 能做什么，就在 Harness 里给它搭什么能力。包括文件系统让它能持久化存储、沙箱让它能安全执行代码、记忆系统让它能跨会话学习、压缩机制防止它在长任务中性能衰减。</font>

#### Loop Engineering
**<font style="color:rgb(134, 134, 139);">定义是：</font>**<font style="color:rgb(134, 134, 139);">给任务定一个准出标准，不达标就回去继续干，直到过线。</font>

Loop Engineering到底改变了什么？<font style="color:#8A8F8D;">之前的工作模式是我写 prompt、Agent 干活、我检查结果、再写下一个 prompt，我才是那个驱动循环的人。有了 Loop Engineering 之后，我设计好目标、评估标准和工具集，然后一个循环系统自动去驱动 Agent，我只在最后看结果。</font>

但这里有一个关键的前提，我后来才想明白——Loop Engineering 真正适用的场景，<font style="color:#8A8F8D;">是那些停止条件可以被明确验证的任务。比如"让所有测试通过"或者"构建成功"，这些条件 Agent 自己能判断。但对于"做一个好的 PPT"这种任务，什么是好本身就很模糊，你还是需要在循环中介入判断。</font>所以 Loop Engineering 解决的是重复执行的自动化，而不是判断好坏的自动化，这个边界很重要。

#### Graph Engineering
Graph Engineering简单的说就是<font style="color:rgb(134, 134, 139);">，把多个Agent Loop连成显示的图，而不是把所有东西塞在一个聊天上下文里。</font>

而他的一个比较明显的特点就是<font style="color:rgb(134, 134, 139);">这个些AgentLoop之间，联系了起来，交给了系统自动推进。</font>

所以他解决问题是<font style="color:rgb(134, 134, 139);">不同任务之间的流程依赖人来推动，效率就不高，这里是交给系统来推动</font>

但这里和我们项目所描述的状态还有一定的距离，<font style="color:rgb(134, 134, 139);">我们再把人工介入加进去，就变成了HITG（Human in the Graph）,也就形成了我项目所描述的</font><font style="color:#8A8F8D;">人和Agent的新协作方式：“系统管流程、Agent 管执行、人管关键决策”。</font>

#### 三者关系
+ **Harness Engineering**<font style="color:rgb(134, 134, 139);">：给 Agent 搭一套环境，让它能更稳定地干活。</font>
+ **Loop Engineering**<font style="color:rgb(134, 134, 139);">：给任务定一个准出标准，不达标就回去继续干，直到过线。</font>
+ **Graph Engineering**<font style="color:rgb(134, 134, 139);">：把多个Agent Loop连成显示的图，而不是把所有东西塞在一个聊天上下文里。</font>
