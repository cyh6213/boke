群聊工作流实战：零代码搭一个会"主动推进"的多 Agent 协作群

我没有写一行编排代码，也没有自建工作流引擎。我只是在一个飞书群里，把一个 Agent 变成"调度员"，把其他 Agent 和人变成"干活的角色"，让一条原本要盯一周的跨平台审核流程，自己往前跑。

这篇文章讲清楚：为什么这么做、它是怎么跑起来的、以及它和真正的工作流引擎差在哪。

为什么我把工作流搬进了群聊

我在字节做广告机审运营的 AI 提效。一类核心工作是搭机审策略：给短视频、广告这些内容配置审核规则。一条策略从无到有，要经过资料查询、策略搭建、结果审查、跨系统流转，中间还夹着因为权限和安全原因必须由人来做的审批。

提效的第一步很自然：把流程里每个能自动化的能力，逐个做成独立 Skill / Bot。这个阶段解决的是单点提效——查资料有查资料的 Bot，搭策略有搭策略的 Bot。

但真正用起来之后，瓶颈不在"某一步能不能自动化"，而在步与步之间：

  • Agent 干完一步，停下来等人看结果；
  • 人把任务派出去，又得等着 Agent 做完；
  • 跨平台时，人还要手动把上一个系统的产物复制、整理、喂给下一个 Bot。

人实际上在充当调度器：记住现在到哪一步了、该叫谁、上下文是什么、做完没、然后通知下一个角色。时间被大量等待和协调切碎。这和有没有 Skill 无关——缺的不是某个能力，而是一个持续管理流程、主动往前推的东西。

核心问题：为什么一个 Agent、一堆 Skill 都不够

我试过让一个 Agent 从头干到尾，也试过把一堆 Skill 摊开手动调用，都不理想。根因有四个：

1. 权限是割裂的，而且卡得最死。 从关键平台取数、在审核系统里建流程，只能由字节内部的 Agent 操作。这些内部 Agent 进不了我自己写的系统，但它们都能被拉进飞书群。这是整个方案的约束前提：编排载体必须是群聊，而不是我自建的程序。

2. 单 Agent 跑长流程，必然劣化。 一个 Agent 执行全部任务，上下文一长，就很难全程遵循 SOP——它会忘记"这一步该让人介入了"，会在切换任务时跳步、漏步，执行质量明显下降。

3. 双向等待把时间打碎。 Agent 等人、人等 Agent，流程的推进依赖某一方"想起来该动了"。

4. 上下文要人肉组织。 每跨一个平台、每转一次手，都得有人把前因后果重新捋一遍再贴过去。

结论：我需要的不是更强的单点能力，而是一层编排——把确定性的"流程推进"从人和模型手里收回来，交给一个专职角色。

设计哲学：流程图交给主控 Agent，执行交给群里的角色

我个人项目里有个概念叫 Graph Engineering，一句话是"系统管流程、Agent 管执行、人管关键决策"。在群聊里，这句话原样成立，只是编排引擎的载体变了：

我自研的 GraphHarness（技术侧） 群聊工作流（业务侧 / 本文）
流程定义 声明式 workflow JSON（DAG） 主控 Agent 的 SOP Prompt（结构化流程卡）
运行时引擎 Orchestrator 代码 + 状态机 主控 Agent 在群里靠消息维护状态
执行者 Agent Runtime 节点 被 @ 的子 Agent（各自绑 Skill）
质量门禁 校验 + 重试 独立的审查 Agent，打回触发回环
人工节点 HITL HITG：把人当成一种特殊"子 Agent"，@ 他干活
依赖推导 从图的边自动算 从 @ 关系和话题回复自动体现

两个核心借鉴，和正式工作流引擎完全一致：

  • 声明式流程：我只描述"做什么、先后顺序、谁来做、什么条件算过、不过打回给谁"，不描述执行细节。流程是一张稳定的图。
  • 运行时状态机：每个步骤有明确状态，状态之间有确定的流转规则。只不过这台状态机不是代码跑的，而是主控 Agent 读着 SOP、盯着群消息在跑。

代价是牺牲了一部分确定性（流转靠模型遵循 prompt，而非代码强约束）；但因为是多 Agent 调度，主控的上下文很短（只装 SOP + 当前节点状态），它的可控性反而比"一个 Agent 包打全程"高得多——跳步漏步几乎消失。

框架架构：一个群，四种角色

                 ┌─────────────────────────────┐
                 │      主控 Agent（调度员）      │
                 │  读 SOP · 维护状态 · 派发      │
                 │  收结果 · 判断下一步 · 主动推进 │
                 └──────────────┬──────────────┘
        ┌───────────────┬───────┴────────┬────────────────┐
        ▼               ▼                ▼                ▼
  ┌───────────┐  ┌───────────┐   ┌─────────────┐   ┌───────────┐
  │ 资料子Agent │  │ 搭建子Agent │   │ 审查 Agent   │   │   人(审批)  │
  │ 绑查询Skill │  │ 绑搭建Skill │   │ 不执行,只门禁 │   │ 关键决策点  │
  └───────────┘  └───────────┘   └─────────────┘   └───────────┘
        各自在独立"话题"里工作，上下文互相隔离
  • 主控 Agent（Orchestrator）：配置了全流程 SOP。负责理解任务、维护当前进度、在群里 @ 对应的子 Agent 或人、收集结果、判断下一步。它自己不干活。
  • 子 Agent（Worker）：每个绑定一类任务的 Skill。只在被 @ 的那个话题（thread）里工作，天然上下文隔离，互不污染。
  • 审查 Agent（Reviewer）：独立角色，不参与执行，只在子 Agent 产出后按预设准出标准检查；不通过就打回，形成回环。
  • 人（HITG，Human in the Graph）：被建模成一种特殊子 Agent。需要人操作的节点，主控 @ 具体的人，并直接给齐"当前任务上下文 + 检查对象 + 要做什么"，人做完在群里回复，主控检测到回复后继续。人不需要回头翻整段流程。

状态机：群聊里的节点生命周期

正式引擎有七种状态，群聊里每一种都有对应表现，主控就是靠识别这些状态来推进的：

状态 群里的表现 主控 Agent 的动作
todo 待派发 还没轮到 等前置节点完成
running 进行中 已 @ 子 Agent，话题里在干活 等该话题回复
review 待审查 子 Agent 交活 @ 审查 Agent，附产物和准出标准
rework 回环 审查不通过 把审查意见 @ 回执行方，重做
blocked_user 等人工 需审批 / 信息不足 @ 具体人 + 给齐上下文与操作要求
blocked_external 等外部 等内部平台 / 审批系统返回 挂起，定时巡检回来捞结果
done 完成 产物落群 / 落文档 推进下一节点

"主动推进"到底靠什么？ 两个机制：

  1. 事件驱动：主控监听群消息和话题回复。谁回复了、产物到了、人审批了，它就把对应节点从 blocked/running 推到下一个 ready，自动 @ 下一个角色。全程不需要人催。
  2. 定时兜底：对于"等外部系统"的节点，没有消息事件可等，主控就定时巡检回来捞结果（这正是我另一条"定时巡检主动预警"链路的思路），避免流程死等。

声明式 SOP：流程怎么写

和 workflow JSON 只描述结构、不写运行态一样，主控的 SOP 也只写流程骨架和准出标准，运行到哪一步由主控在群里动态维护。一张流程卡长这样：

# 策略搭建 SOP

- step: query_material   角色: 资料Agent   做什么: 查策略所需素材与历史case
  准出: 素材清单齐(≥N条)且来源可追溯        下一步: build
- step: build            角色: 搭建Agent   做什么: 在审核平台搭建策略
  准出: 策略保存成功且配置完整              下一步: review
- step: review           角色: 审查Agent   做什么: 按准出标准检查策略
  准出: 通过 → approve                     不通过 → 打回 build(带意见)
- step: cross_system     角色: 搭建Agent   做什么: 流转到下游系统
  准出: 下游回执成功                        下一步: approve
- step: approve          角色: 人(@负责人)  做什么: 审批上线
  准出: 人在群里回复"通过"                  下一步: archive
- step: archive          角色: 主控        做什么: 归档产物并通知

关键约束和正式引擎一致：SOP 里只写"做什么 / 谁做 / 准出 / 下一步 / 打回给谁"，不写 status、不写当前上下文。这样流程卡干净、可读、可复用——同类任务换个输入就能再跑一遍。

实际案例：一条机审策略在群里是怎么自己跑完的

我：在群里发起"给 XX 场景搭一条策略"，附上初始资料。

  1. 主控读到 SOP，第一步是 query_material，@ 资料 Agent 开了个话题，把需求贴进去。
  2. 资料 Agent 在话题里查完，回复素材清单。主控识别到该话题有产物 → 节点 done。
  3. 主控自动 @ 搭建 Agent，并把素材清单作为上下文带过去（不用我复制）。
  4. 搭建 Agent 建完策略回交。主控 @ 审查 Agent，附上策略和准出标准。
  5. 审查发现规则有漏召，打回：主控把意见 @ 回搭建 Agent（rework 回环），重做后再审，通过。
  6. 流转下游系统后，到 approve：主控 @ 我（负责人），直接给出"策略链接 + 变更点 + 需要你确认什么"。
  7. 我在群里回"通过"。主控检测到回复 → 归档、通知，流程 done。

整个过程里，我只在第 7 步真正做了决策。其余的推进、转交、上下文组织、打回重做，都是主控在做。

怎么搭（零代码）

  1. 拆能力：把流程涉及的能力逐项做成独立 Skill / Bot（单点提效阶段的产物）。
  2. 建群拉人：把能用的内部 Agent 都拉进同一个飞书群——它们进不了我的代码，但都能进群。
  3. 写主控 SOP Prompt：给主控一份结构化流程卡 + 推进规则（模板见下）。
  4. 约定协议：每个子 Agent 只在自己被 @ 的话题里干活；主控靠 @ 和话题回复判断流转。
  5. 跑一条再补：先用真实任务跑一遍，把每步的"准出标准"补明确——准出越可验证，审查和自动推进越靠谱。

主控 SOP Prompt 模板（可直接改）：

你是本群的流程调度员，严格按下面的 SOP 推进，不要自己执行具体任务。

【推进规则】
- 每一步只 @ 对应角色，并在消息里给齐：该步目标、所需上下文、准出标准。
- 子 Agent 在独立话题里工作；它在话题回复产物后，你判断准出是否满足：
  满足 → @ 下一步角色；不满足且该步有审查 → 带意见打回重做。
- 需要人时，@ 具体的人，写清"检查对象 + 要做什么"，人回复后再继续。
- 等外部系统的步骤，不要死等，每隔一段时间回来检查一次结果。
- 全程用一张状态清单记录：每个 step 当前是 待派发/进行中/待审查/打回/等人/等外部/完成。

下载并使用这个 Skill

为了让这套群聊工作流不只停留在思路层面，我把主控 Agent 的角色定义、状态维护规则、@ 协作协议、审查回环和人工介入规则封装成了一个可复用的 Skill。你不需要从零写整份 Prompt，只需下载 Skill，并根据自己的业务替换角色和 SOP，就可以搭出一条会主动推进的群聊流程。

下载「群聊工作流」Skill

如何使用

1. 下载并启用 Skill

点击上方按钮进入 Skill 页面，下载或添加到支持 Skill 的 Agent 平台，并将它启用为群聊中的主控 Agent。这个 Skill 负责维护流程和派发任务，不负责替代所有子 Agent 执行具体工作。

2. 准备群聊角色

把流程需要的角色拉进同一个群：

  • 一个启用了本 Skill 的主控 Agent；
  • 若干绑定了查询、搭建、流转等能力的子 Agent；
  • 一个只做结果校验的审查 Agent；
  • 需要执行审批或关键决策的负责人。

3. 提供业务 SOP

把自己的流程按“步骤、执行角色、输入、准出标准、下一步、失败后回到哪里”整理成流程卡，发给主控 Agent。可以直接使用前文模板，也可以先用自然语言描述，让主控整理后由人确认。

示例 Prompt：

请使用群聊工作流 Skill 管理下面的任务：
目标：完成一条 XX 场景的机审策略搭建并推进至审批。

参与角色：
- 资料查询：@资料Agent
- 策略搭建：@搭建Agent
- 结果审查：@审查Agent
- 最终审批：@负责人

流程：
查询资料 → 搭建策略 → 审查 → 跨系统流转 → 人工审批 → 归档。
审查不通过时返回“搭建策略”，并把审查意见一同带回。
开始前先输出流程和角色映射，待我确认后再执行。

4. 确认流程并启动

主控会先输出流程步骤、角色映射和人工介入点。确认无误后回复“开始执行”，它会从第一个就绪节点开始 @ 对应角色，并在每个节点完成后主动推进。

5. 只处理被 @ 的关键节点

执行过程中不需要持续盯群。只有流程进入 blocked_user 时，主控才会 @ 负责人，并附上决策所需的上下文、待检查对象和具体操作。回复处理结果后，主控会自动续跑。

6. 查看结果与运行记录

流程结束后，让主控输出一份汇总：各节点状态、关键产物、审查与返工次数、人工介入记录、异常情况。群消息本身也保留了完整执行轨迹，方便复盘和追溯。

效果

  • 单条策略搭建周期从一周缩短到两天，大量等待和协调时间被消掉。
  • 人的角色从"流程调度者"变成"关键决策者"，不用一直盯住单条任务，可以同时管多条流程。
  • 跨平台上下文由主控自动组织，不再人肉复制。
  • 因为主控上下文短、只认 SOP，跳步漏步基本不再出现。

Skill 编排与 DAG 引擎有什么区别

这套群聊方案和我的 GraphHarness 都在解决同一个问题：如何让多 Agent、工具和人围绕一条流程持续协作，而不是每做一步都等人手动推进。 但两者不是同一种实现。最大的区别是可控制性。

Skill 本质上仍是一份结构化 Prompt：它把 SOP、角色分工和流转规则交给模型理解，再由模型判断当前状态与下一步。因此它提供的是语义层面的软约束。DAG 则把节点、依赖、条件分支和状态转移编码成机器可执行的数据结构，再由 Orchestrator 调度，提供的是运行时层面的硬约束。

例如，同样面对“审查失败后回到搭建节点，最多重试三次”：

  • Skill 方案是告诉主控 Agent“失败后回到搭建，最多三次”，依赖模型正确计数、选择节点并携带上下文；
  • DAG 方案会显式记录当前节点、重试次数和跳转边。只有满足条件的节点能进入 ready queue，超过阈值则由状态机强制进入异常分支。

这不是“一个高级、一个低级”，而是两种不同的工程取舍。

Skill 方案的优势：不是“简单”，而是“够轻”

1. 零代码、启动快。 业务人员只需写 SOP、配置角色，不必搭建服务和运行时。很多流程可以先跑起来，再决定是否值得工程化。

2. 对变化更宽容。 真实业务经常临时插入一步、换负责人、补一份材料。自然语言编排能直接理解这些非结构化变化，不必每次修改 DAG。

3. 能绕过系统接入的现实障碍。 我无法把内部 Agent 接进个人项目，却能把它们拉进群。群聊把权限已经存在的角色组织起来，比重新申请 API 和凭证更可行。

4. 人机协作自然。 人和 Agent 在同一条消息流里。主控可以直接 @ 人、补齐上下文并等待回复，不需要额外开发审批页面和回调协议。

5. 天然可视化。 业务人员能直接看到谁在做什么、卡在哪里、为什么打回。相比后台 Trace，群消息更符合非研发人员的使用习惯。

Skill 方案的缺点：可靠性上限由 Prompt 决定

  • 模型可能误判状态、遗漏步骤或错误选择分支，Prompt 只能降低概率，不能从机制上禁止；
  • 上下文过长或历史消息被截断后，主控可能丢失早期状态；
  • 对重复执行、并发写入和外部副作用缺乏强一致性保障；
  • 流程越长、条件越复杂，Prompt 的维护难度和不可预测性越高；
  • 很难做严格的自动化测试，复现同一条执行路径也更困难。

DAG 方案的优势：把“应该这样做”变成“只能这样做”

DAG 与 Harness 的核心价值不是流程画得更漂亮，而是将关键控制权从模型推理转移到系统：依赖是否满足、哪些节点可以并行、失败后跳到哪里、最多重试几次、从哪个 Checkpoint 恢复，都由确定性代码负责。Agent 只在节点内部处理需要语义理解和工具调用的不确定任务。

因此，DAG 方案更适合线上生产、高风险操作和长时间运行的任务，也更容易做版本管理、自动化测试、Trace、指标统计和故障复现。

它的代价同样明显：开发和接入成本高；每个外部平台都需要 API、凭证和适配器；流程频繁变化时需要修改、校验和发布；对一个还没证明价值的业务流程来说，可能过早工程化。

两者不是替代关系，而是一条演进路径

我更倾向于把它们看成一条从业务验证到工程生产化的路径：

  1. 先用 Skill 跑通。 用最低成本验证流程是否稳定、哪些节点可自动化、哪里必须有人、准出标准是什么。
  2. 再把稳定骨架固化成 DAG。 当流程高频运行、风险上升或 Prompt 误差不可接受时，把节点、依赖和状态迁移到 GraphHarness。
  3. 节点内部继续使用 Skill。 DAG 负责确定性的流程控制，Skill 负责节点内部的语义执行。两者结合，形成“外层 DAG 管流转、内层 Agent/Skill 管执行”的分层架构。

也就是说，Skill 版本不是 GraphHarness 的竞争方案，而是它的低成本原型和业务验证层；GraphHarness 则把已验证的流程升级成稳定、可观测、可恢复的生产系统。

一句话总结：Skill 用自然语言换取灵活性和低门槛，DAG 用工程复杂度换取确定性和可控制性。最合理的方案不是二选一，而是让 DAG 管流程，让 Skill 管节点。

适用场景

这套模式不挑业务内容，挑的是结构。只要一个任务同时满足——流程骨架相对固定、由多个相互依赖的子任务组成、数据和操作分散在不同系统、部分节点因权限/风险/判断必须有人介入——就适合：合规审核、运营活动上线、内容生产审批、故障排查、采购申请、软件发布……

它们业务不同，结构相同：确定性的流程骨架 + 不确定性的执行节点 + 不可缺少的人工决策点。
