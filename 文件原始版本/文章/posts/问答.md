## RAG 项目介绍（三个阶段）

关于 企业知识库RAG 项目，这个项目主要分为了三个阶段。

第一阶段主要围绕企业知识库这个场景，搭建 RAG 的基础链路，学习各种策略来提升召回率、降低幻觉率。同时基于企业知识库的实际需求，做了文档上传优化、权限控制等工程化的工作。

第二阶段是将 RAG 变成了一个 Agentic RAG，主要做了两件事情，一个是智能路由，尝试对简单问题进行分流，减少不必要的向量检索；另一个是针对不同任务设计针对性的检索策略，比如需要多次检索的问题、对比类的问题等。

前两个阶段我其实没有系统的测评过，所有的优化都是"看起来有提升就觉得有效"，但实际提升了多少我并不清楚。所以在阶段三，我系统性地搭建了测评体系，对检索和生成两个环节分别做了多轮消融实验，让每一次优化都能看到具体的数据变化。也就是在这里我发现了一个问题，学到的最关键的一点就是，不是看起来合理的优化策略就真的有效，要基于实际数据做评估。

## RAG 是什么？解决了什么问题？

RAG（检索增强生成）是为了解决大模型的三大问题：

首先是知识的时效性，在训练好的那一刻就固定了；其次是专业性不足或者说不知道私有知识；最后是幻觉问题，他没有说不知道的能力，只能瞎编。

RAG 就是在调用大模型前，先从知识库里检索相关内容，塞到 Prompt 里，让大模型"看着资料回答"。可以让新知识随时入库解决知识时效性的问题；公司文档入库解决私有的问题；让 LLM 有参考内容、可溯源，解决幻觉的问题。

### GraphRAG 是什么？

主要是为了解决向量数据库 RAG 的两个问题：**全局问题**（比如技术路线是怎么演变的）和**关系问题**（公司A和公司B的间接关系是什么），不是靠检索出一两个分片就可以解决的。

**GraphRAG 的原理**就是将文档切块，提取实体和关系，构建一个图，然后将联系紧密的地方分区，变成社区，最后生成社区摘要。在进行检索的时候，针对关系问题，就是提取实体，然后扫描一圈他的关系；针对全局问题，就是通过社区摘要，选低层级社区 → 答案更细致，但是成本更高，选高层级社区 → 答案更概括。

**GraphRAG 的问题**就是 Token 消耗多（提取实体关系、生成摘要等）、增量更新难（导致社区的拆分重组）、社区的颗粒度难定（层级太高太笼统，层级太低社区数量爆炸，成本上升）。

于是又出现了 **LightRAG**，简单点说就是他没有了社区结构（来减少更新的复杂度），增加一层用下层的关系建立的图，用来解决全局问题，代价就是全局性问题没有 GraphRAG 那么厉害，别人的社区相当于是提前就生成好了答案。

**如何选择？**（Token消耗、要求高低、更新频率）
● 如果是非结构化文本（比如新闻、客服场景），低成本场景，就使用向量 RAG。
● 如果是要求高、钱多，就使用 GraphRAG。
● 中间平衡的，且更新较为频繁的，就用 LightRAG。

## 召回率优化：RAG 基础链路

RAG主要分为三部，包括上传、检索、排序，如果再加上生成就是四步。

**上传阶段**，主要就是文件的解析和分块策略。我的项目中实现的是两级四层的语义分块策略，我也了解其他的策略，但成本都比较高。我还做了并发上传和异步的文件解析，来减少上传时间，提升用户体验。

**检索阶段**，主要是问题改写、召回策略。问题改写在智能路由那里针对不同的问题有不同的改写策略。召回策略我使用的是Milvus数据库，BAAI/bge-m3的向量模型，使用稠密向量 + 稀疏向量作为召回策略。在这一步将 recall_cap@5 提升到了76.66%。

**排序阶段**，主要有三种排序方式，包括根据两种召回按照权重排序，按照排名进行排序，以及通过Rerank重排序。最后选择的是Rerank重排序将recall_cap@5 最终提升到了81.2%。

**生成阶段**，我主要通过Prompt优化、结构化输出约束、低分拒答、幻觉检测机制、调低temperature、top-p等五个策略来减低他的幻觉率。最后使用了RAGAS框架，对忠实度、答案相关性等参数进行了测评。

### 幻觉优化：5项降低幻觉策略

**本质**：模型在生成过程中，过度自信地"编造"了信息。

**原因**：大模型生成本质是根据概率输出，所以天然会偏；Decoder 逐词生成，一旦某一步注意力权重偏了，后续全在这个错误上堆叠；并且向量没有"我不知道"这个状态，遇到知识盲区模型不会沉默，而是用最流畅的语法硬编一个错答案。

**类型**：
① 训练数据没有包含、检索没有召回到相关内容，导致 LLM 没有可用的上下文，靠自身知识在编造答案。
② 检索内容召回了但 LLM 没有严格遵循，在文档内容的基础上加了自己的推断。

**解决**：
**针对没有找回到相关内容：**
**① Prompt 约束** — 让他没有的就说不知道

**② 低分拒答** — 如果混合检索或者 Rerank 得出来的分数过低，就直接回复没有资料，而不是让大模型对着不相干的内容硬编。

**针对 LLM 添加私货的情况：**
**③ 结构化输出** — 让 LLM 输出结构化的结论，每个结论都必须填写来自哪条参考资料。

**④ RAGAS 核查** — 生成后再调用一次 LLM 核查或者使用 RAGAS 来做核查，来检查忠实性、答案相关性。

**⑤ 参数调低** — 把 temperature、top-p 等参数调低，让他回答的更严谨，避免跑偏。

### 检索阶段有哪些测评指标？

除了 recall_cap@5，还测试了以下 6 项指标，共 7 项全面对比：

**recall_cap@5** — 在前 5 个检索结果中，包含至少一个相关文档的比例。cap=5 表示只考虑前 5 个结果，衡量"能否在前 5 个中找到相关文档"。基线 68.4% → 最优 81.2%。

**recall@5** — 在前 5 个检索结果中，召回的相关文档占所有相关文档的比例。衡量"召回覆盖率"。基线 56.5% → 最优 67.5%。

**ndcg@5** — 归一化折损累计增益，相关文档排得越靠前分数越高。衡量"排序质量"。基线 71.6% → 最优 82.1%。

**mrr@5** — 第一个相关文档出现位置的倒数均值。衡量"最快多久能找到第一个相关结果"。基线 85.6% → 最优 91.1%。

**precision@1** — 第一个检索结果就是相关文档的概率。衡量"首条命中率"。基线 82.6% → 最优 88.2%。

**f1@5** — 前 5 个结果的精确率和召回率的调和平均。衡量"精确率与召回率的平衡"。基线 47.9% → 最优 57.3%。

**端到端延迟** — 从发起检索到拿到结果的总耗时。纯向量检索约 55ms，增加 Rerank 后约 360ms（+305ms，在可接受范围内）。

### 分片

关于分片，主要有以下四种策略。

#### 为什么要分片？

① Embedding 模型有输入长度限制，超长文本会被截断丢失信息。

② 长文档可能含多主题，整体向量化导致语义稀释。

③ 模型的输入有限，更精确的检索出相关信息可以节约空间。

#### 两层四级语义分块策略

我们的分片策略第一层 · 父块流式解析，达到 parentChunkSize（1MB） 自动切割，而不是把整个文章加载到内存再分块，避免 OOM。第二层 · 子块（四级语义切割）将父块文本按 chunkSize 512 TOKEN 分割为更小的子切片① 优先按段落分割（

）
② 段落过长按句子分割
③ 句子过长按词语分割（HanLP 分词，不拆词）
④ 最后兜底按字符分割
全程保证语义完整性，不会把完整句子、词语强行切断。重叠分块每个分块的前后都有一部分"上下文冗余"，这样，embedding 模型在处理时就不会遗漏关键信息。

#### 其他分片策略

**固定大小**

**按照层级**（章节、内容），适合结构清晰的文档

**按照语义**

**特殊内容：**代码（以函数为单位）、表格（要保留表头，可以转化为json）

**父子：**检索用小分片，返回大分片

**语义补全：**用LLM给每一个分片都生成一个上下文，代价就是成本高

#### 代码分片策略

代码分片策略切片部分我用 JavaParser 类做 AST 分析，把源代码解析成语法树，然后遍历树节点提取类和方法的起止行号，再根据行号从原始代码中提取对应文本。

这种方式的优势在于能够保持代码的语义完整性，不会像按字符数分段那样切断方法或类，同时还能获取类名、方法名等元数据，为后续的代码检索和分析提供更丰富的信息。

类 chunk 只提取前 5 行作为类签名，不会把整个类的代码都塞进去。长方法目前没有做二次切分，实际项目中超过这个长度的方法比较少见，真要改善可以按内部逻辑块继续拆分。

### 问题改写的5种策略

**① 简单改写** — 处理口语化查询，消除代词补充隐含信息。

**② 问题拆解** — 把多个问题拆解分开查询，还有对比类问题，A手机和B手机的性能对比，分开查询然后对比输出。

**③ HyDE** — 让LLM生成假设答案，用答案向量去检索，因为答案和专业文档的用词更接近，语义匹配度更高。

**④ 多角度扩写** — 把查询改写成3到5种表述分别检索后合并去重，覆盖不同作者的用词习惯。Query扩展补充相关关键词，扩大召回范围。

**⑤ 后退提问** — 把具体问题抽象到通用原理层面，先检索背景知识建立上下文，再检索具体细节。

## 检索核心技术详解

### 为什么要混合检索？

**关键词检索**基于经典的倒排索引和词频统计，比如说 BM25 算法，将用户的查询拆解成关键词。精确匹配能力强，但无法理解语义。

**语义检索**使用深度学习模型将查询和文档转换为向量，通过计算向量间的距离来衡量语义相似度。能理解同义、近义和上下文关系，但可能对精确的术语或数字不敏感。

**混合检索**融合了关键词和语义检索策略，通常通过 RRF 等算法综合排序。

生产环境推荐采用混合检索的原因：单一检索策略有天然短板。用户的真实提问可能包含精确术语，也可能包含模糊的自然语言。混合检索能兼取两者之长，在不牺牲精度的情况下提升召回率，从而提高 RAG 系统的整体鲁棒性和准确率。

### 向量检索的原理

首先就是向量化，用 Embedding 模型将原始数据转化为向量，长文档转化为向量前需要分块，然后用嵌入模型将分好的块转化成向量。然后再是检索。

**长度**代表内容的多少，信息量的大小
**角度**代表语义

检索主要有三种方式：

**余弦相似度**：计算两个向量的夹角，夹角越小，就越近。只看方向。

**欧式距离**：计算两个向量的距离，距离越小，就越近。

**点积**：计算两个向量方向一致性与长度的数值（l1*l2*cos），结果越大通常表示向量越相似。既看方向，又看长度。需要归一化，也就是长度差异特别大时，有的向量明明角度很大，但是可能被长度掩盖。

一般会使用余弦相似度，因为只看方向不看长度，更适合衡量语义相似度，不会受到文本长度的影响。

### BM25 原理

ES 默认的关键词相关性算法，根据词频、文档长度计算匹配度。会通过两个关键词控制匹配度：

**k1**：越大，关键词频率对匹配度影响就越大
**b**：越大，对长文档的惩罚就会越重（相同词语出现次数，文章越长，匹配度越低）

### 稀疏索引、稠密索引与关键词检索的区别

**稠密向量**：把文本压缩成一个固定维度（如 2048 维）的浮点数向量，每个维度"均匀分摊"了语义信息。优势是能理解语义相似度，缺点是精确匹配差——搜"鲁迅"可能把"周树人"拉进来。

**稀疏向量**：把文本映射成一个超高维（几万到几十万维）的向量，但大部分维度是 0，只有少数维度有值。每一个维度对应一个具体的词或 token，值表示这个词的重要性。既保留了关键词级别的精确匹配能力，又具备向量空间的距离计算能力。比 BM25 强的地方在于它可以用学习到的词权重，而不是纯统计的 IDF。

**关键词检索（BM25）**：基于词频统计的精确匹配算法，只计算查询词与文档中相同词的匹配程度。速度快、可解释性强，但无法理解同义词、近义词等语义关系。

稀疏向量是稠密向量和关键词的一个"中间态"：下接关键词的精确性（每个维度对应具体词），上接稠密向量的语义理解（可做向量空间的距离计算）。这也是为什么双路召回用稠密 + 稀疏搭配效果最好：稠密负责语义泛化，稀疏负责精确命中。

### RRF 重排序

在多路排序列表中，忽略不同排序方式的分数，只看排名的一种排序方式。

**好处**：可以忽略不同排序方式的分数
**缺点**：因为它忽略了分数，所以不包含分数信息。比如一个文档的相关性是100，第二名是1，但根据排名来说，一个是1/1，一个是1/2，相关性差距就不大。

**倒数打分**：每个列表里，按位置算分 1/(k+rank)
**分数累加**：同一文档在所有列表中的得分求和
**重排输出**：按总分从高到低排序，得到融合结果
**k**：平滑常数，默认 60；k越大，得分越平均，更重视"出现次数"而非"靠前程度"；k越小，第一名优势越强，适合强头部场景。

### ReRank 原理

**Embedding 模型（Bi-Encoder）**：分别计算 Query 和文档的向量，然后对比相似度。好处是快、可以全库搜索。但是只看到了表面的匹配，没有做深度交互。

**Rerank 模型（Cross-Encoder）**：它会把 Query 和文档拼接在一起，直接分析每个词之间的关系，而不是先生成向量再比较，让它能够更深度地理解 Query 和文档的关系。最后输出一个 0 到 1 之间的相关性分数。代价：速度慢，开销大。

所以一般是先用 embedding 搜广度，再用 Rerank 精细化。

## 智能路由

智能路由主要有两个目的，一方面是希望能过滤出不需要向量检索的问题，以此来减少查询API的调用和缩短流程时间；另一方面是通过对不同类型的问题制定针对性的检索策略，以此来弥补向量 RAG 在多跳推理、全局性关联等需要逻辑链的场景上的固有短板，以此提高检索出来内容和回答的质量。

而要实现这两个目标，需要做两件事情，第一件是问题分类，第二件是问题处理。

**问题分类**我设计了两层机制，包括通过关键词和正则匹配快速过滤简单（闲聊、纯计算）问题，通过模型来对问题进行分类。

**针对第一个目标**，实际测评下来发现这个方案有三个问题，第一检索管线只占总耗时的一小部分，第二简单问题的占比也不高，第三如果通过规则进行问题分类的准确度较低，会让不是简单问题的问题跳过检索，而如果使用模型来进行分类，虽然可以提高分类的准确率，但是耗时增加大于缩短，得不偿失。所以让我意识到：优化不是看起来合理就行，需要有测试数据验证。

**针对第二个目标**，不同类型查询的处理差异主要体现在检索策略、改写深度、上下文组装方式和生成策略四个维度。我举个例子：比如问题是产品A和B的区别是什么？就会执行两次独立检索分别放入A池和B池。单边缺失标注信息不足，禁止用模型知识填补空白。输出按维度对比表格。再比如假如问题是程愚瀚和鲁迅的关系是什么，就需要执行多次向量检索，每步基于前序结论动态构建新查询——程愚瀚是电子科大的学生，然后电子科大又有什么人才，然后就可以和鲁迅联系上了。在检索使用较低阈值（0.6）做宽召回。在生成时要求标注推理步骤。当然，开启之后耗时就会长很多。

## 权限控制

## 🔧 Workflow 项目介绍

## 项目起源与方案对比

关于这个项目，我主要从三个方面来讲：项目的起源、为什么我能够继续去做这个项目、可复用的经验。

**首先是项目起源**
我发现 Agent 在执行任务时经常会遇到跳步遗漏的问题。比如要求他进行 30 条测试，他只运行了 10 条；或者我要求他在输出之前必须先检查一下，结果他直接跳过了检查这一步。

我想到了两种方式来解决这个问题：Workflow 和 Hooks，最后选择了 Workflow。

一般的 Workflow 是由人来定义的，比如说扣子这种低代码平台。但是在这里，我将 plan 的工作交给了 Plan Agent 来完成。

所以最终的方案就是：Plan Agent 构建 DAG 图，将 DAG 图可视化展示给用户确认，再用执行引擎读取 DAG 图自动完成任务，确保规划了就一定会执行。

**然后是为什么我能够继续去做这个项目**
在做这个项目的过程中，我发现单纯说解决跳步遗漏这个问题，DAG 这个策略也没有那么好。但是这个项目还有一些其他的优点，比如可以使用到长链路任务的场景，解决目标偏移的问题；并且基于 DAG 图还可以实现更高效的并行执行策略、断点恢复、harness 这三个优点。

**最后是可复用的经验**
我在这个项目也学到了一些可以迁移的东西，比如如何调整 prompt 来优化 Agent 完成一个固定任务、Token 优化、异常治理、agent 测评等。

### DAG策略的局限性

DAG这个策略也没有那么好（具体不好在哪里）

**vs PAE（Plan and Execute）**
相较于PAE，DAG实现起来比较复杂。PAE在粗颗粒的任务上做的比较好（比如检索再生成），但是在细颗粒度的做的比较差，比如要求测试30条数据可能只测试了10条。

**vs Claude Code 的 Dynamic Workflow**
相较于claudecode的dynamic workflow来说，它是通过写JavaScript脚本来控制流程，所以相对来说，它的控制更加细致，会更加灵活。它想解决的问题是单个agent在长链路任务中懒惰、目标漂移的问题。

## Plan 优化

想要Agent能够帮你执行好一件事情，主要就是三个策略：第一个是给他说清楚你要做什么，第二个是列举清楚规则是什么，第三个是举一些例子。这就是Prompt Engineering里面最基本的操作。

然后我为了保证这个DAG图它是没有环的，以及做一些其他的检测，我还设置了一个后置的校验层对它进行校验。

Prompt + 样本 + 校验做到位了，DAG质量有了基本保障。但模型会犯错，而且同样的错误可能反复出现——这就需要一套机制让Plan能力能自己不断变好。于是我就参考了Reflexion的思路，把每次执行失败的DAG当作负样本收集起来，自动分析失败原因，再把高频错误注入到Prompt和样本中。这样每次失败都变成一次教学，Plan的能力就随着使用次数越来越多，形成一个持续改进的闭环。

## 节点输入输出（STAR法则）

关于这个问题我可以按照STAR法则来讲。

**Situation — 背景**：节点之间有明确的先后依赖关系，后面的节点需要拿到前面节点的输出才能执行。原本的做法直接把子Agent的完整对话历史——包括system prompt、工具调用、工具返回结果、中间推理过程——全部传给下一个节点。然后就会遇到一个问题，多个节点串联后，下游Agent的context窗口很快被占满。

**Task — 目标**：需要确定每个节点的输出应该包含什么内容、以什么格式输出，下游节点能拿到什么内容。来实现下游节点只拿到它真正需要的信息，控制上下文占用。

**Action — 方案与权衡**：关于以什么格式输出这一点，我想出来了两个策略，第一个是压缩，把完整的对话历史压缩成摘要，再传给下一个节点。但问题在于压缩本身也是一次模型调用，会额外消耗token，而且压缩后的摘要可能会丢失细节。于是我选择了借鉴Dynamic Workflow的动态Schema格式化输出，在生成DAG图的时候，就确定好他需要输出什么内容。关于下游节点能拿到什么内容，不再是拿到这一条链路的全部输出，而是只拿到前一个节点的输出。

**Result — 效果**：节点传递的信息量被控制在原始输出的10%到20%左右，也不再有上下文堆积的问题。

## Harness

**为什么要设计 Harness？（问题 + 方案 + 好处）**

**问题：**
我的系统里，一轮任务的执行链路远比表面看起来复杂。它不是简单地把任务丢给 Plan Agent 就结束了：前面有 DAG 生成和校验，中间有拓扑解析、Sub Agent 分发、上下文动态构建和节点调度，后面还有结果收集、状态持久化、Trace 记录和流式输出。

如果把这些逻辑全部塞进 Plan Agent 里，就会出现两个问题：一是 DAG 校验、AI 推理、数据库、Trace 记录、状态管理这些不同性质的东西会全部混在一起，代码非常难维护；二是这些逻辑一旦和模型耦合，后面想换 Plan 模型或调整执行策略，都会牵连一大片。

**方案：**
所以我这里就做了一个职责分类，调用方只负责发起请求和接受执行结果，Plan Agent 只负责 DAG 生成，Sub Agent 只负责单个节点的执行，而 Harness 负责将他们联系起来，包括 DAG 校验、拓扑解析、Sub Agent 分发与上下文构建、状态持久化和 Trace 记录。

**好处有三点：**
第一，把不稳定的模型行为和确定的执行逻辑分开。Plan Agent、Sub Agent 的输出是不确定的，但 Harness 的校验规则、调度算法和异常处理都是写死的代码，输出是确定的。这样做的意义是：一方面，换模型不影响执行层，改执行策略也不需要动规划层，排查问题不用纠结到底是模型的问题还是逻辑的问题；另一方面，用一套可靠的代码去承接和校验不可靠的模型输出——即使 Plan Agent 规划得再离谱，Harness 也会在正式执行前拦截校验，这也就是 harness 系统的定义，去做一个缰绳。

第二，让每一层职责单一。调用方，Plan Agent，Sub Agent只需要负责自己的事情。Harness 作为中间的编排者，把跨切面逻辑集中起来。

第三，可测试性。我可以单独用 Harness 执行一组预设的 DAG 数据来测并行调度是否正确、异常分支是否走对了、Trace 是否完整记录，不需要启动完整的 Plan Agent 和前端界面。

### Harness 的定义是什么？

Harness 这个概念本质上是在回答一个问题：为什么同样一个模型，在不同的产品里表现天差地别？答案就是 Agent 等于模型加 Harness，模型提供的是智能引擎，而 Harness 是让这份智能真正落地的那套系统。

一个裸模型本质上只是一个文本输入输出的函数，它记不住上下文、执行不了代码、访问不了实时数据。Harness 就是围绕这个函数搭建的一整套基础设施，包括文件系统让它能持久化存储、沙箱让它能安全执行代码、记忆系统让它能跨会话学习、压缩机制防止它在长任务中性能衰减。

这些东西的设计原则是从期望的 Agent 行为逆向推导的，你想要 Agent 能做什么，就在 Harness 里给它搭什么能力。所以 Harness Engineering 本质上是一种系统工程思维，它承认模型的智能是不完美的，但通过设计好的环境、工具和反馈循环，可以让任何模型在特定任务上发挥出远超其本身的能力。

### Run Trace

**Trace**

Run Trace 保存的是一条执行链路从开始到结束的完整运行轨迹，而非最终结果。它会记录 Plan Agent 产出的原始 DAG 图、校验环节是否检测到环路及修复过程、每批并行拆分的节点列表、每个 Sub Agent 执行时的输入输出和状态、异常触发时的策略和重试次数、条件分支的选中路径。并统一落库。

它的作用在于让排查和复盘能有依据，让管理员和开发者看到每一步的动作、输入、输出和采纳理由。可以追问：Plan Agent 为什么这么规划 DAG、校验层有没有发现问题、异常触发时用了什么策略、重试了几次、条件分支为什么选了这条路。

### 为什么 Redis 和 MySQL 都要用

**存储：为什么 Redis 和 MySQL 都要用**

Redis 负责短期上下文。每轮对话需要快速读取最近会话窗口——历史消息、记忆摘要、当前 session 状态。这些数据读写频繁、结构简单、单条体积小，Redis 的 TTL 机制天然适合控制短期记忆的无限增长。

业务数据库负责完整留痕。完整的会话记录、心理报告、Trace、工具任务、管理员审计记录需要有可靠持久化。Redis 有淘汰策略，可能被清理，不适合承担审计和风控留档。数据库提供结构化查询和关联追溯的能力。

两者配合：每轮优先从 Redis 取短期上下文，读写快；Redis miss 时从数据库回填。写入时双写——短期上下文的变更刷入 Redis，完整的业务记录落数据库。这样既保证了响应速度，也不丢失长期留痕。

## 双层并行执行引擎

第一层是通过图来实现并行，入度（In-Degree）指一个节点被多少条边指向，入度为0表示该节点没有任何前置依赖，可以直接执行。每执行一个节点就将其指向的节点的入度减一，于是就会有新的可执行节点出现。直到将所有节点执行完毕。

第二层是在agent的react模式，支持他同格式调用多个工具，比如同时读取多个文件。

## 节点级断点恢复

设计了三张表来记录一个DAG图的执行。

一张表存DAG拓扑结构，第二张存每个节点的输入输出和状态，第三张存整次执行的全局汇总。（运行时的数据传递纯走内存HashMap，节点执行完顺手把快照同步写入MySQL，但不从数据库读。）

当断点继续触发时，就会从第二张表读出快照恢复到内存，结合第一张表重新解析的DAG图确定从哪个失败节点开始，跳过已成功的，接着往下跑。最后把第三张的状态从FAILED改回RUNNING，执行完再更新。

## Sub Agent 分发执行

做出将子任务交给子agent是水到渠成的，首先是设计到并行执行，所以不能是一个agent。其次是我总结出了三个优点。

第一点是每个agent只需要负责他们自己的任务，放在长链路的任务中，可以解决目标偏移的问题；

第二点是我们可以针对每一个agent的身份，控制他们能调用的skill或者tool，来实现权限控制和提高他们调用skill、tool的正确率；

第三点是我们减少了默认的、不必要的skill、tool注入，也就减少了单次的token消耗。并且由于我对子agent之间的信息传递做了格式化输出，所以不会出现上下文堆积的情况，也就进一步减少了token消耗。

## Token 优化

包括三点。

第一点由于我们设计了不同类型的子agent，所以针对性的设计了他可以调用的skill、tool，也就减少了默认的、不必要的skill、tool注入，也就减少了单次的token消耗。

第二点是，由于我对子agent之间的信息传递做了格式化输出，抹去了大量的工具调用等信息，以此减少了下一个节点的输入。

第三点是，控制当前节点只会获取前一个节点的输出，而不是这一条链路的输出，所以不会出现上下文堆积，也就是后一个节点的上下文包含前面所有节点的输出的情况，也就进一步减少了token消耗。

## 异常治理

因为这个项目采用固定DAG执行，相比PAE架构可根据前一步结果动态修改下一步计划的方式，丧失了执行中调整流程的能力。而三级异常治理就是为了弥补这一限制而设计的。

首先是在顶层设计了while循环来处理重试，在第二层设计了超时策略，在最底层设计了异常捕获，又分为三种处理方式：

① 直接中断 — 关键节点失败后整体进入失败状态。适用于支付、扣款、核心写操作等。

② 错误码策略 — 按预配置的错误码或默认值继续执行。适用于辅助查询、非核心推荐等。

③ 失败条件分支策略 — 引导到异常处理分支，用于告警、补偿、回滚或特定兜底逻辑。

## 条件分支路由

条件分支路由是为了解决有些情况Plan Agent不知道这一步的结果是什么，遇到不同的结果可能会有不同的路径。但这里就遇到一个问题：我们的并行策略是把一排节点拿来并行执行，但遇到条件分支的话，难道要同时执行两个分支吗？于是我就设计了condition字段——只有匹配条件的边才会被激活，来解决这个问题。

## Agent 测评

**测什么**
我觉得首先是要明确测什么，包括两个方面，结果和过程。结果维度包括需求完成度、耗时、Token消耗，过程维度包括工具调用链、无效ReAct循环、异常处理等。然后针对不同的Agent场景也需要有不同的测评，比如我们这里的DAG构建正确率，或者说CodingAgent的代码质量等。

**怎么测**
然后是怎么测，主要分为了三个方面，包括设计测评集、设计评分器、选择测试方法。

**测评集的设计**
首先是测评集的设计，要注意质量比数量更重要。我这里因为人手的原因，我是先让Agent帮我设计了一批样本，覆盖常规流程、并行分支、复杂拓扑、边界样本和对抗样本，我再去挑选和修改。

**设计评分器**
然后是设计评分器，包括两种，确定性评分器和LLM-as-Judge。非常清楚的可以看出来当需要理解的部分就需要调用大模型，其他时候更适合使用确定性评分器，因为大模型的评分不稳定，使用确定性评分器能够更直观的看出来改进。比如在测试DAG图构建率时，就是使用的确定性评分器，通过查看有没有环的出现来得出分数。

**测评方法**
最后就是选择测评方法，比如基准测试（在标准数据集上跑分，与基线版本或竞品横向对比）、回归测试、AB测试等。我觉得在agent测试中，回归测试比较重要。因为对prompt的修改指不定就破坏了已有能力，所以需要做回归测试去确保新改动不破坏已有能力。

## 💡 通用概念

## Agent

### Agent 是啥？和普通的 LLM 有什么区别？

Agent 除了 LLM，还包括了记忆、工具模块。让他拥有了记忆和实践能力，成为了能够真正执行任务的工具，而不只是回答问题。

然后再通过 ReAct、Plan-and-Execute、Reflection 等策略，让 agent 拥有反思总结、多步骤的能力，就可以让他任务执行的更好。

### Agent 有哪些设计范式？如何选择？

**ReAct** 就是推理、行动、观察的循环，推理这一轮我需要干什么，行动获取结果，再根据结果思考是在进行下一轮还是结束循环返回结果。问题是他只能看见眼前，处理特别复杂的、需要全局规划的任务时，容易在中间迷失方向。

**Plan-and-Execute** 是先制定计划-执行-再加上动态判断（可能提前结束或者重新规划）。

**Reflexion** 是在完成当前任务之后，反思做的好不好，如果评估不通过，就重试或者换一种策略。他还有一种变体，就是会记录错题本。记录下这次失败的原因和改进建议，然后把这段总结作为额外的上下文传给下一次尝试。

**如何选择？** 如果是一个任务，就适合使用 ReAct；如果是有多个步骤，链条比较长的任务就适合使用 PAE。三种设计范式可以混合使用，用 Plan-and-Execute 做整体规划，每个步骤内部用 ReAct 来执行。如果要求比较高需要迭代的，就再加上 Reflexion。

### Multi-Agent（多智能体）协作范式有哪几种典型架构模式？

四种标准架构：主从、流水线、对等、混合。

**主从架构** — 1 个调度主 Agent + N 个专业子 Agent。主 Agent 拆解总任务、分配子任务、汇总所有子 Agent 结果。子 Agent 只负责单一细分能力，无全局决策权。优势是管控简单、输出统一；劣势是主 Agent 单点瓶颈。

**流水线架构** — Agent 按固定顺序串联，前一个输出作为后一个输入。Agent1 输出→Agent2 接收处理→Agent3 收尾。优势是适合线性工序任务；劣势是某一环失败整体阻塞，无并行能力。

**对等架构（去中心化）** — 所有 Agent 地位平等，通过 A2A 互相通信协商、自主分工，无统一指挥官。各 Agent 自主认领擅长任务，互相交换信息，冲突自主协商。优势是分布式、可并行、容错高；劣势是交互逻辑复杂，容易出现分工混乱。案例：多个专业 AI 专家共同完成一份行业报告。

**混合架构** — 融合以上两种及以上模式，大型项目主流方案。比如主 Agent 做任务拆分（主从），拆分后的子任务分组走流水线并行处理。

### 单 Agent 范式和多 Agent 范式的边界在哪里？

**单 Agent：**一个大模型实例承载全部能力，内部靠提示词、记忆、工具完成所有子步骤，所有决策由同一个模型做出。适合任务复杂度低、能力维度单一、子任务无强专业隔离的场景。

**多 Agent：**多个独立 Agent 各司其职，每个 Agent 专精一类能力，通过 A2A 互通信息，任务拆解到不同智能体分工完成。适合任务跨多领域、能力互相冲突、单一模型无法兼顾所有专业逻辑的场景。

## MCP 是什么？

**是什么？**
我理解的 MCP 它就是一个 agent 到 tool 之间的一个协议，它能够让 agent 调用这个 tool，避免每一个 agent 对接每接一个新工具都要单独写适配代码。底层基于 JSON-RPC 2.0 实现有状态双向通信，支持本地 stdio、HTTP-SSE、流式 HTTP 多种传输方式。

**协议有什么组成？**
有三部分：Host、Client、Server。Host 就是支持 MCP 协议的应用程序，也就是我们配置大模型的地方。Client 在 Host 内部运行，负责与 MCP Server 建立连接。Server 可以理解为一个软件，我们将他提供的原子性的能力称之为 Tool，一个 Server 可以提供多个 Tool。

**怎么使用？**
当我们配置并启动我们需要的 Server 后，会获取其包含的 Tool 列表，用户提问后，Host 将问题与 Tool 列表一同传给模型；模型判断需调用的 Tool 及参数，反馈给 Client；Client 转发调用请求至 MCP Server，Server 执行 Tool 后返回结果；Client 将结果回传给模型，模型整理后给出最终答案并反馈给用户。

**项目体现**
然后包括我的这个 RAG 项目，我也把它实现成了一个 MCP。我当时想象的场景就是说，我是一个程序员，我肯定不会使用我公司开发的 RAG 来帮我执行一些任务。但是我使用其他如 Claude Code 来执行任务的时候，我又需要获取我公司的资源，怎么办？那我可能就通过公司的 RAG 的 MCP 的一个工具来获取一些资料，然后让 agent 能够更好的帮我完成这个任务。

## FunctionCalling 是什么？（和 MCP 的关系是什么）

Function Calling 主要包括四部分：大模型主动识别需求（让模型知道什么时候该输出普通文本，什么时候该输出工具调用 JSON）、生成结构化参数、调用外部工具（解析返回的函数名和参数，调用真实接口 / 本地函数）、拿到结果再整合回答。让 Agent 有了调用外部工具的能力。

**Function Calling 和 MCP 的关系**
Function Calling 解决的是"模型怎么调用工具"的问题，是模型能力层面的；MCP 解决的是"工具怎么被模型发现和调用"的问题，是协议层面的。两者是互补关系：Function Calling 让模型能调用工具，MCP 让工具能被模型发现和调用。

### 如何让大模型格式化输出？

有三种方式：

**① 原始阶段（Prompt）**：通过 prompt 写清楚 JSON Schema 的例子，但是 prompt 的约束不稳定。

**② 指令微调 SFT**：在 SFT 阶段喂了大量"问题-答案"对，让模型学会识别什么时候需要调用工具、按固定格式输出函数名+参数、不乱说废话，直接吐结构化数据。

**③ 输出时的强约束机制**：模型是根据概率生成字符，通过微调仍然可能输出不符合规范的内容，这时候就可以通过 JSON Schema、正则（用来匹配字符串格式的专用语法）、状态机过滤，将不符合规范的字符概率设置为 0。

### 格式化输出 2.0（约束解码）

约束解码：大模型生成文本是一个 token 一个 token 往外蹦的。正常情况下，每一步模型会算出一个概率分布，然后从所有 token 里选一个。但结构化输出做了一件事：在每一步生成之前，先根据 JSON Schema 算出一个"当前合法的 token 集合"，然后把不合法的 token 的概率全部置为零，模型只能在合法集合里选。

但是好像国产模型不支持，而是通过微调实现的。我检索了一下说是成本问题：约束解码需要在模型推理的时候，每生成一个 token 都跑一遍状态机，检查当前 token 是否合法。这个状态机本身不贵，但它会破坏推理的批处理（batching）。大模型厂商为了降成本，会把多个用户的请求拼成一个 batch 一起算，这样 GPU 利用率高。但约束解码意味着每个请求的合法 token 集合不一样——你的 Schema 是 {name, age}，别人的 Schema 是 {city, temperature}，两个请求的合法 token 集合不同，就没法拼在一起算了。要么只能单独算（降低吞吐），要么用更复杂的调度策略（增加工程成本）。

## Skill 是什么？（和 MCP 的关系）

**Skill 是什么？**
Skill 可以理解为解决特定任务的固定规则，是一种知识的沉淀，来实现策略的复用和传播。

**有什么组成？**
整体采用渐进式披露机制，由三层组成，第一层元数据始终加载，包括名称和描述，让模型决定使用哪一个 skill；第二层流程层，描述怎么做（流程、规则、约束条件，以及使用哪一个 tool，加载哪一个材料）；第三层资源层，是进一步的按需加载，包括资源、示例、脚本、甚至其他的 skill 等。比如我在写一个 skill 的时候，为了避免这个 skill 包含不同任务的内容，我就会在这个 skill 中写明，当他遇到什么问题的时候，去访问某一个子 skill。这样能够减少上下文浪费。

**和 System Prompt 的区别是什么？**
● System Prompt 是一段静态的全局的文本指令，它只影响 LLM 的生成风格、角色设定、行为边界等，没有执行逻辑，无法调用外部系统或改变状态。
● Skill 是一个可执行的、结构化的能力单元，包含元数据、输入参数定义、状态管理等。Skill 能被 Agent 动态调度、组合、复用。

**Skill 冲突了怎么解决？**
假如说用户的需求很模糊，这个时候同时命中多个 Skill 那会造成冲突，主要有四种解决方式：

① LLM 二次决策 — 将用户输入 + 候选 Skill 列表一起给 LLM，要求输出最匹配的一个，或者输出"需要澄清"。

② 优先级 + 置信度打分 — 给每个 Skill 预设一个 priority，数值越小优先级越高。同时使用 embedding 相似度得出匹配分。取分数最高且 priority 最小的。

③ 定义互斥规则 — 定义某些 Skill 不能同时匹配，比如说 send_email 和 send_sms 被同一句话触发时，配置优先走 email。

④ 用户历史偏好 — 记录用户最近使用过的 Skill，在冲突时优先匹配历史 Skill。

## Harness Engineering 是什么？

Harness 这个概念本质上是在回答一个问题：为什么同样一个模型，在不同的产品里表现天差地别？答案就是 Agent 等于模型加 Harness，模型提供的是智能引擎，而 Harness 是让这份智能真正落地的那套系统。

一个裸模型本质上只是一个文本输入输出的函数，它记不住上下文、执行不了代码、访问不了实时数据。Harness 就是围绕这个函数搭建的一整套基础设施，包括文件系统让它能持久化存储、沙箱让它能安全执行代码、记忆系统让它能跨会话学习、压缩机制防止它在长任务中性能衰减。

这些东西的设计原则是从期望的 Agent 行为逆向推导的，你想要 Agent 能做什么，就在 Harness 里给它搭什么能力。所以 Harness Engineering 本质上是一种系统工程思维，它承认模型的智能是不完美的，但通过设计好的环境、工具和反馈循环，可以让任何模型在特定任务上发挥出远超其本身的能力。

## Loop Engineering

Loop Engineering 到底改变了什么？之前的工作模式是我写 prompt、Agent 干活、我检查结果、再写下一个 prompt，我才是那个驱动循环的人。有了 Loop Engineering 之后，我设计好目标、评估标准和工具集，然后一个循环系统自动去驱动 Agent，我只在最后看结果。

但这里有一个关键的前提：Loop Engineering 真正适用的场景，是那些停止条件可以被明确验证的任务。比如"让所有测试通过"或者"构建成功"，这些条件 Agent 自己能判断。但对于"做一个好的 PPT"这种任务，什么是好本身就很模糊，你还是需要在循环中介入判断。所以 Loop Engineering 解决的是重复执行的自动化，而不是判断好坏的自动化，这个边界很重要。

Loop Engineering 和 Reflection 的对比：Reflection 是 Agent 内部的一次推理过程中自我反思的机制，本质上是模型在生成回答之前的内部循环。而 Loop Engineering 完全不同，它是外部的、跨多次 Agent 调用的编排框架，解决的是让 Agent 能够稳定地长时间自主运行的问题，比如无限循环、任务中断、资源超额消耗这些在实际落地中才会遇到的坑。所以它和 Reflection 不在一个层次上，Reflection 解决的是单次推理的质量，Loop Engineering 解决的是整个任务执行的可靠性。

## SpecCoding（SDD规范驱动开发）

规范驱动开发，也就是先写规格文档（包括需求分析、技术方案、各种 rule）然后再生成代码的开发模式。其实我们想一下也知道，我们想让人完成一个项目需要什么，那让 agent 完成一个项目也就需要什么。如果像 vibecoding 一样，只告诉他一个很模糊的需求，那就很难得到你想要的结果。

我觉得规格文档（也就是所有不属于代码的文档）应该划分为两部分：

**第一部分**是可以所有项目共享的 rule 和模板，这一部分也就是我们可以不断迭代浓缩。我之前看过得物发的一个文档，里面详细规划了三层 rule，包括基础层（代码的格式、注释的规范）、模块层（代码的架构规范）、流程层（开发流程等各种流程），模板则是指第二部分的规范。

**第二部分**是和这个项目内容有关的，比如需求分析、变更记录等。agent 或者如果是在企业多人开发的时候，就可以通过这些记录对这个项目有一个大概的感知，而不是去全部扫描一遍代码。我在 spec coding 的时候发现，把这些详细的记录落到文件，会极大的增强我对代码的自信心和了解程度，不像我在 vibecoding 的时候，跟开盲盒一样，也不清楚哪一个类是干什么的。

## Transformer

### Transformer 原理？为什么比 RNN 好？

RNN 有两个致命缺陷，直接导致了 Transformer 的出现。

**长距离依赖丢失。**RNN 处理文本是一个词一个词顺序读的，靠一个叫"隐状态"的向量把前面读过的信息传给下一个词。问题在于这个传递是有衰减的——读第 50 个词的时候，第一个词的信息已经被反复压缩得面目全非了，这就是著名的梯度消失问题。好比传话游戏，传了 50 个人之后，第一句话早就变味了。

**无法并行计算。**因为 RNN 必须读完第 i 个词才能读第 i+1 个，整个序列只能串行处理。这意味着 GPU 虽然有几千个计算核心同时闲着，也只能一个接一个排队算，训练效率极低。对于需要处理几百万篇文章的大模型来说，这根本不可接受。

所以 Transformer 核心就是通过**自注意力机制**让每个词能同时看到句子里所有词，既没有长距离信息衰减，又能一次性并行计算整个序列。

**自注意力机制的简要流程：**每个词可以同时生成三个向量——Q 是"我在找谁"，K 是"我是谁"，V 是"我要说什么"。每个词拿自己的 Q 和所有人的 K 做点积打分，Softmax 归一化成权重，再按权重把所有人的 V 加权求和，最终每个词都变成了融合全场上下文的向量。

● 长距离依赖方面，第 1 个词和第 500 个词之间是直接计算的，没有层层传递的衰减，打分高低只看语义关系不看距离远近。
● 并行计算方面，所有词的 Q、K、V 可以一次性算出来，矩阵乘法一把梭，GPU 的几千个核心终于不用排队了。

代价就是，注意力矩阵是 N×N 的，序列长度翻倍计算量翻四倍，这就是上下文窗口不能无限大的根源。

### Temperature、Top-P、Top-K 原理？怎么控制大模型输出随机性？

大模型工作原理：模型输出分为三步，分别是给所有词汇生成分数（Logits）、通过 Softmax 函数将分数转换为概率、按概率加权采样选词输出。

● 模型输出原理：给他认识的每一个词打分，谁分高就输出谁，接着循环，直到输出一个完整的句子，遇到了结束标记。问题是：这样输出就固定了，于是就将分数转化为概率。
● 通过 Softmax 函数将分数转换为概率：于是输出下一个词就不再一定是分数最高的，而是分数越高，概率越大。
● 最后按概率加权采样选词输出。

**Temperature 原理：**该参数作用于 Softmax 函数，通过调整分数缩放比例改变词汇概率差距；数值越低高分词概率越集中、输出越稳定，数值越高词汇概率越平均、输出越随机多样。

**Top-p 原理：**全称最高累加概率，是概率阈值参数，从高分词开始累加概率至阈值后截断长尾低概率词，避免输出跑题；数值越低过滤词越多、输出越严谨，数值越高兼容词越多、输出越发散。

**Top-k 原理：**和 Top-p 差不多，这个是选取前 k 个，那个是选取前 p 的概率。

**参数核心区别与使用建议：**Temperature 调整词汇概率差距，Top-p 截断长尾词汇；二者值越大越适合创作发散场景，值越小越适合代码、数学等严谨场景，OpenAI 建议仅调整其中一个参数即可。

### 什么是 KV Cache？Prompt Cache 缓存命中原理是什么？

首先是误区：现在的 LLM 的架构都是 decoder（包括训练和输出），所以他就是单向的注意力机制，所以就只会看左边。流程跟有没有 encoder 差不多，第一步是计算 kv，区别就是 encoder 是双向，decoder 是单向，然后第二步都是 decoder 利用前一步的 kv，计算输出。

而 **KV Cache** 指的就是缓存 kv，因为现在两步都是 decoder，KV Cache 包括这两步的 kv 缓存。用在第一步，就是缓存相同 prompt 前缀的 kv，因为每一个 token 的 kv 都是根据前面的 token 来计算的，所以不变就可以不重新计算，变了就需要重新计算。用在第二步就是循环的 decoder 计算输出，下一个词语的输出会依据上一个词的 kv，这里会存起来，就不用重新计算。

### 大语言模型是怎么炼成的？Transformer 的训练流程？

大语言模型的训练分为三个阶段。

**阶段一：预训练**
做法是把互联网上几乎所有公开文本（书籍、论文、网页、代码）丢给模型，让它反复做一件事——预测下一个词。这属于自监督学习，不需要人工标注，语料本身就是标签。
关键点：预训练让模型掌握了语法、常识、推理模式，知识量远超任何人。但不听话，它只会文本接龙，不懂你让它做什么。

**阶段二：SFT 监督微调**
提供大量高质量"问题-答案"对，覆盖日常问答、写作、翻译、代码等场景，然后用这些数据继续训练模型。
关键点：模型学会了指令遵循和对话格式，知道"当用户这样说时，我应该那样答"。但学来的东西好坏都吸收。标注员可能带入偏见，模型也可能学会迎合而非求真。只教了"做什么"，没教"不做什么"。

**阶段三：RLHF 基于人类反馈的强化学习**
具体分三步：
● 首先对同一个问题让模型生成多个答案，人类标注员给这些答案做偏好；
● 然后用这些偏好数据训练一个奖励模型，让它学会判断"人类更喜欢哪种回答"；
● 最后用奖励模型配合 PPO 算法去微调 LLM，让模型生成更符合人类偏好的输出。
关键点：生成更符合人类偏好的输出，包括：判断什么该答、什么该拒绝、什么该承认不知道、要懂礼貌、不要胡说等。

**阶段四：LoRA**
全参数微调要更新整个模型所有矩阵，百亿参数起步，普通显卡根本跑不动。LoRA 不碰原始权重 W，只在旁边挂两个小矩阵 A 和 B。计算时输出 = W·x + B·A·x，训练只调 A 和 B，W 冻结不动。因为 A、B 是低秩矩阵，参数量只有原来的千分之一。

### 为什么必须分阶段训练？

不合并成一步，有三个原因。

**成本：**预训练极昂贵。如果在预训练阶段就使用昂贵的人工标注数据，成本将是天文数字。把"学知识"和"学规矩"分开，最大化利用免费互联网数据，只在最后关键步骤用人工。

**稳定性：**三个目标有时冲突。让一个还没学会基本语言规律的模型同时去学复杂的"人类偏好"，学习过程会极不稳定，最终可能什么都没学好。

**灵活性：**一次昂贵预训练得到一个强大基座模型，然后针对不同场景（写代码、写小说、做客服）用不同微调和 RLHF 派生出各种专业模型。一次筑基，多次复用。

### BPE 分词算法

BPE（Byte Pair Encoding，字节对编码）是目前主流大模型分词器的核心算法。

**训练过程分四步：**
● 初始状态：词表只含基础字符（英文就是 26 个字母加标点，中文就是常用单字）
● 统计整个语料库中所有相邻符号对的共现频率
● 合并频率最高的字符对，生成新 Token（比如 t + h → th，再 th + e → the）
● 重复合并，直到词表达到预设大小（如 5 万）

**训练结果：**高频词变成大积木（"the"、"apple" 各为一个 Token），低频词拆成子词拼装（unfortunately → ["un", "fortunate", "ly"]），生词也可以组合推断（unfriendly → ["un", "friend", "ly"]）。

### 内存压缩策略

每轮循环开始前：
1. L3 大结果落盘（先把大的存起来，防止后面擦掉）
2. L1 裁中间（擦掉旧的对话）
3. L2 旧结果占位（旧输出换成一行提示）

如果还不够：
4. L4 LLM 摘要（花钱让模型写摘要）

如果 API 还报错：
5. 应急裁剪（更激进地擦）

他设计了一个四层压缩策略。前三层是不需要调用 LLM 的文本操作，分别是大输出结果落盘到磁盘只留预览（前 2000 字）、裁剪旧对话、旧工具结果用一行占位符代替。如果前三层跑完还是太大，才触发第四层 LLM 摘要，花一次 API 调用让模型生成包含当前目标、重要发现、剩余工作等关键信息的摘要，替换所有旧消息。还有应急方案，API 报错时以更激进的方式从尾部回退裁剪（留下更少的对话）。

### 上下文压缩的具体实现

我觉得最核心的有两个设计，一个是在生成摘要前引入了一个草稿本机制，另一个是把摘要的输出分成了九个固定段落。这两个设计解决的是不同层面的问题，但组合在一起效果非常好。

草稿本
它的做法是让模型在输出正式摘要之前，先复盘整个对话，再输出 <summary>。这个设计的"思考"和"输出"能够换取更好的压缩质量。这个 <analysis> 在后续处理时会被直接删掉。

九段模板
这九段包括：
● **要干什么**
○ 目标
○ 背景（列出所有讨论过的重要技术概念、技术和框架。）
○ 所有用户消息
○ 待办
● **干过什么**
○ 代码（逐一列举已检查、修改或创建的具体文件和代码段。附上完整代码片段，并说明为什么这次读取或编辑很重要。）
○ 错误（列出你遇到的所有错误，以及你如何修复它们。特别关注用户给出的具体反馈，尤其是用户让你换种方式做的时候。）
○ 已解决的问题（避免了重复劳动）
● **要干什么**
○ 当前状态（压缩发生时正在干什么）
○ 下一步（下一步要干什么，必须附上最近对话的逐字原文引用）

### 长期记忆

**结构**
核心是一个单独的 MEMORY.md 文件，充当目录角色，每次对话启动时默认加载前 200 行到 system prompt。记录了每一个记忆的文件名和一句话描述。

然后是四种记忆类型不是用文件夹物理隔离，而是通过文件名里的 type 字段逻辑标记，分为 user（偏好）、feedback（规矩）、project（项目背景）、reference（线索） 四类。

**写入触发机制**
第一条是被动存储，当用户说了某些特定内容时触发，比如"记住""别忘了"这类关键词。这些场景下模型会主动把信息写入记忆文件。

第二条路径是主动提取，对话结束后后台会自动 fork 一个子 agent，让它分析整个对话内容，从中识别出符合记忆类型的信息并自动提取保存，用户不需要显式说"请记住这个"。

**注入机制**
第一层是 MEMORY.md，每次对话启动时默认加载前 200 行到 system prompt。

第二层是按需检索，在每轮对话前把 MEMORY.md 连同当前用户查询发给一个轻量级的模型，让它从中选出最多 5 个最相关的记忆文件，注入到当前对话上下文。

**"后台整理"机制**
它每 24 小时运行一次，模拟人类睡眠时的记忆整合过程。它的作用主要是：
● 扫描记忆内容，合并相同内容，移除过时内容，确保 MEMORY.md 文件的精干。

### SystemPrompt

Claude Code 的 system prompt 是运行时组装的，分为静态和动态两类。

静态段落包括身份定义、语气风格、任务处理原则、工具使用说明等，这些是每轮对话都需要的核心指令，内容基本稳定。

动态段落包括记忆注入、会话指导、MCP 服务器指令、token 预算控制等，这些根据当前状态决定是否加载，比如记忆段落只在有记忆文件时才注入。

组装时每轮对话前会检查上下文真实状态，基于这些状态决定加载哪些段落，然后拼接成完整 prompt。

## OpenClaw 和 Hermes 的区别

**定位**
OpenClaw 是网关调度型企业 Harness，靠配置预制技能，无自主进化。Hermes 是原生 Agent 运行时，内置自学习，能自动沉淀复用任务流程。

**记忆 & 安全**
OpenClaw 是单层会话记忆，仅黑名单做命令拦截。Hermes 三层持久记忆，多级沙箱 + 高危人工确认，对齐 Claude Code Harness。

**适用场景**
OpenClaw 适用多渠道客服、政企强合规标准化任务。Hermes 适合本地编码、对接 Claude Code、个人长期自动化。

## 你想从这个岗位学到哪些技术相关的东西？

**问：你想从这个岗位或实习中学到哪些技术相关的东西？**

**第一，**想学大规模 Agent 的工程化落地经验。我之前做的 Agent 项目都是跑几条测试数据，这个岗位每天几十万条审核数据，能学到真正的生产环境怎么处理吞吐量、成本控制和稳定性，还有 Agent 出错后怎么兜底。

**第四，**Agent 编排平台的实战经验。我之前是自己写框架搭 Agent，想学一下扣子这类成熟平台是怎么设计 Agent 编排的，反过来对自己做 Workflow 项目也有帮助。
