## <font style="color:rgb(51, 65, 85);">RAG项目</font>
#### RAG 的基础链路
RAG主要分为三部，包括上传、检索、排序，如果再加上生成就是四步。

在**上传**阶段，主要就是文件的解析和分块策略。我的项目中实现的是两级四层的语义分块策略，我也了解其他的策略，但成本都比较高。我还做了并发上传和异步的文件解析，来减少上传时间，提升用户体验。

在**检索**阶段，主要是问题改写、召回策略。问题改写在智能路由那里针对不同的问题有不同的改写策略。召回策略我使用的是Milvus数据库，BAAI/bge-m3的向量模型，使用稠密向量 + 稀疏向量作为召回策略。在这一步将 recall_cap@5 提升到了76.66%。

在**排序**阶段，主要有三种排序方式，包括根据两种召回按照权重排序，按照排名进行排序，以及通过Rerank重排序。最后选择的是Rerank重排序将recall_cap@5 最终提升到了81.2%。

在**生成**阶段，我主要通过Prompt 优化、结构化输出约束、低分拒答、幻觉检测机制、调低temperature、top-p 等五个策略来减低他的幻觉率。最后使用了RAGAS框架，对忠实度、答案相关性等参数进行了测评。

#### 智能路由
智能路由主要有两个目的，一方面是希望能过滤出不需要向量检索的问题，以此来减少查询API的调用和缩短流程时间；另一方面是通过对不同类型的问题制定针对性的检索策略，以此提高检索出来内容和回答的质量。

而要实现这两个目标，需要做两件事情，第一件是问题分类，第二件是问题处理。

问他分类我设计了两层机制，包括通过关键词和正则匹配快速过滤简单（闲聊、纯计算）问题，通过模型来对问题进行分类。

但是针对第一个目标，实际测评下来发现这个方案有三个问题，第一检索管线只占总耗时的一小部分，第二简单问题的占比也不高，第三如果通过规则进行问题分类的准确度较低，会让不是简单问题的问题跳过检索，而如果使用模型来进行分类，虽然可以提高分类的准确率，但是耗时增加大于缩短，得不偿失。所以让我意识到：优化不是看起来合理就行，需要有测试数据验证。

针对第二个目标，不同类型查询的处理差异主要体现在检索策略、改写深度、上下文组装方式和生成策略四个维度。我举个例子：比如问题是产品A和B的区别是什么？就会执行两次独立检索分别放入 A 池和 B 池。单边缺失标注信息不足，禁止用模型知识填补空白。输出按维度对比表格。再比如假如问题是程愚瀚和鲁迅的关系是什么，就需要执行多次向量检索，每步基于前序结论动态构建新查询。程愚瀚是电子科大的学生，然后电子科大又有什么人才，然后就可以和鲁迅联系上了。在检索使用较低阈值（0.6）做宽召回。在生成是要求标注推理步骤。当然，开启之后耗时就会长很多。

#### 权限控制
权限控制主要分为三个方面，登陆控制、角色控制、标签控制。

登陆控制主要是通过Access Token作为核心通行证，有效期 1 小时，减小泄漏风险，通过Refresh Token作为长期凭证，有效期 7 天，泄漏也无法直接调用接口，可通过 Redis 快速吊销。

角色控制则是通过Spring Security，校验用户角色是否有权访问当前接口。

标签控制则是在访问文件时，通过查看用户标签和文章标签有交集，来判断的用户是否有权访问文件。

为什么要实现mcp化：公司员工比如程序员他在写代码的时候，会使用各类agent来辅助，所以实现mcp化之后，这些agent访问企业内部的私域知识时，就不需要员工手动检索，agent可以自己去检索。

#### 双层并行执行引擎
第一层是通过图来实现并行，入度（In-Degree）指一个节点被多少条边指向，入度为 0 表示该节点没有任何前置依赖，可以直接执行。每执行一个节点就将其指向的节点的入度减一，于是就会有新的可执行节点出现。直到将所有节点执行完毕。

第二层是在agent的react模式，支持他同格式调用多个工具，比如同时读取多个文件

#### 节点级断点恢复
设计了三张表来记录一个DAG图的执行。

一张表存 DAG 拓扑结构，第二张存每个节点的输入输出和状态，第三张存整次执行的全局汇总。

（运行时的数据传递纯走内存 HashMap，节点执行完顺手把快照同步写入 MySQL，但不从数据库读。）

当断点继续触发时，就会从 第二张表 读出快照恢复到内存，结合第一章表重新解析的DAG图确定从哪个失败节点开始，跳过已成功的，接着往下跑。最后把第三张的状态从 FAILED 改回 RUNNING，执行完再更新。

#### Sub Agent 分发执行
做出将子任务交给子agent是水到渠成的，首先是设计到并行执行，所以不能是一个agent。其次是我总结出了三个优点。

第一点是每个agent只需要负责他们自己的任务，放在长链路的任务中，可以解决目标偏移的问题；

第二点是我们可以针对每一个agent的身份，控制他们能调用的skill或者tool，来实现权限控制和提高他们调用skill、tool的正确率；

第三点是我们减少了默认的、不必要的skill、tool注入，也就减少了单次的的tooken消耗。并且由于我对子agent之间的信息传递做了格式化输出，所以不会出现上下文堆积的情况，也就进一步减少了token消耗。

#### 节点输入输出
关于这个问题我可以按照star法则来讲。

Situation — 背景：是节点之间有明确的先后依赖关系，后面的节点需要拿到前面节点的输出才能执行。

原本的做法直接把子 Agent 的完整对话历史——包括 system prompt、工具调用、工具返回结果、中间推理过程——全部传给下一个节点

然后就会遇到一个问题，多个节点串联后，下游 Agent 的 context 窗口很快被占满

Task — 目标：需要确定每个节点的输出应该包含什么内容、以什么格式输出，以下游节点能拿到什么内容。来实现下游节点只拿到它真正需要的信息，控制上下文占用。

Action — 方案与权衡：关于以什么格式输出这一点，我想出来了两个策略，第一个是压缩，把完整的对话历史压缩成摘要，再传给下一个节点。但问题在于压缩本身也是一次模型调用，会额外消耗 token，而且压缩后的摘要可能会丢失细节。于是我选择了借鉴 Dynamic Workflow的动态 Schema 格式化输出，在生成 DAG 图的时候，就确定好他需要输出什么内容。

关于游节点能拿到什么内容，不在是拿到这一条链路的全部输出，而是只拿到前一个节点的输出。

Result — 效果：节点传递的信息量被控制在原始输出的 10% 到 20% 左右，也不再有上下文堆积的问题。

#### token优化
包括三点。

第一点由于我们设计了不同类型的子agent，所以针对性的设计了他可以调用的skill、tool，也就减少了默认的、不必要的skill、tool注入，也就减少了单次的的tooken消耗。

第二点是，由于我对子agent之间的信息传递做了格式化输出，抹去了大量的的工具调用等信息，以此减少了下一个节点的输入。

第三点是，控制当前节点只会获取前一个节点的输出，而不是这一条链路的输出，所以不会出现上下文堆积，也就是后一个节点的上下文包含前面所有节点的输出的情况，也就进一步减少了token消耗。

#### Plan 优化
想要 Agent 能够帮你执行好一件事情，主要就是三个策略：第一个是给他说清楚你要做什么，第二个是列举清楚规则是什么，第三个是举一些例子。这就是 Prompt Engineering 里面最基本的操作。

然后我为了保证这个 DAG 图它是没有环的，以及做一些其他的检测，我还设置了一个后置的校验层对它进行校验。

Prompt + 样本 + 校验做到位了，DAG 质量有了基本保障。但模型会犯错，而且同样的错误可能反复出现——这就需要一套机制让 Plan 能力能自己不断变好。于是我就参考了 Reflexion 的思路，把每次执行失败的 DAG 当作负样本收集起来，自动分析失败原因，再把高频错误注入到 Prompt 和样本中。这样每次失败都变成一次教学，Plan 的能力就随着使用次数越来越多，形成一个持续改进的闭环。

#### Agent 测评
我觉得首先是要明确测什么，包括两个方面，结果和过程。结果维度包括需求完成度、耗时、Token 消耗，过程维度包括工具调用链、无效 ReAct 循环、异常处理等。然后针对不同的Agent场景也需要有不同的测评，比如我们这里的DAG构建正确率，或者说CodingAgent的代码质量等。

然后是怎么测，有主要分为了三个方面，包括设计测评集、设计评分器、选择测试方法。

首先是测评集的设计，要注意质量比数量更重要。我这里因为人手的原因，我是先让Agent帮我设计了一批样本，覆盖常规流程、并行分支、复杂拓扑、边界样本和对抗样本，我再去挑选和修改。

然后是设计评分器，包括两种，确定评分器和LLM-as-Judge，非常清楚的可以看出来当需要理解的部分就需要调用大模型，其他时候更适合使用确定性评分器，因为大模型的评分不稳定，使用确定性评分器能够更直观的看出来改进。比如在测试DAG图构建率时，就是使用的确定性评分器，通过查看有没有环的出现来得出分数。

最后就是选择测评方法，比如基准测试（<font style="color:rgb(100, 116, 139);">在标准数据集上跑分，与基线版本或竞品横向对比</font>）、回归测试、AB测试等。我觉得在agent测试中，回归测试比较重要。因为对prompt的修改指不定就破坏了已有能力，所有需要做回归测试去确保新改动不破坏已有能力。

#### 异常治理
因为这个项目采用固定 DAG 执行，相比 PAE 架构可根据前一步结果动态修改下一步计划的方式，丧失了执行中调整流程的能力。而三级异常治理就是为了弥补这一限制而设计的。

首先是在顶层设计了while循环，在第二层设计了超时策略，在最底层设计了异常捕获，又分为分三种处理方式：

① 直接中断 — 关键节点失败后整体进入失败状态。适用于支付、扣款、核心写操作等。

② 错误码策略 — 按预配置的错误码或默认值继续执行。适用于辅助查询、非核心推荐等。

③ 失败条件分支策略 — 引导到异常处理分支，用于告警、补偿、回滚或特定兜底逻辑。
