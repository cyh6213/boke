## 一、项目概述

**项目名称：** 可视化任务编排与执行系统（Workflow 2.0）

**项目定位：** 一个 Plan-and-Execute 架构的 DAG 工作流系统，支持可视化规划、流式执行、AI 辅助修改。核心解决 Agent 不按需求执行的问题——通过 Plan Agent 生成 DAG 图，执行引擎强制按图执行，确保规划了就一定会执行。

**版本演进：**
- **Workflow 1.0（前身）：** AI 工作流编排平台，用户通过拖拽方式搭建 AI 应用。局限性：不智能，所有流程和参数需用户手动定义。
- **Workflow 2.0（当前）：** Plan Agent 根据用户需求动态生成 DAG 执行计划，执行引擎强制按计划执行。
- **Workflow 3.0（构想中）：** Tree，从固定 DAG 走向更灵活、更智能的任务编排。

## 二、项目来源 — 从问题到方案（origin）

### 要解决的问题：Agent 不按照需求执行

使用 Agent 时发现指令明确但 Agent 不执行。比如要求"检索后回答"结果跳过检索直接生成答案。真正的问题是：**Agent 会无视你的指令和规划，自己决定怎么做**。

**典型场景：**
- ❌ 没有 DAG："检索竞品资料后生成分析报告" — Agent 直接生成了一份报告，根本没去检索。
- ❌ 没有 DAG："先查天气再安排行程" — Agent 查完天气后直接给出行程，忘了查交通。
- ❌ 没有 DAG："分析代码质量前先做安全扫描" — Agent 跳过安全扫描直接分析。

### 两种确定化路径

| 方案 | 描述 | 举例 |
|------|------|------|
| **Workflow — 约束流程** | 限制 Agent 在整个流程中必须要做什么 | 强制流程为 [读取财报 → 分析指标 → 生成报告] |
| **Hooks — 约束操作** | 限制 Agent 在某一步前后必须要做什么 | PreHook 检查文件格式，PostHook 检查敏感数据 |

**选择：** Workflow 路径，因为流程层面的约束对"Agent 不按需求执行"这个问题更直接。Hooks 思路可以后续补充，两者不冲突。

### 解决方案

Plan Agent 只负责根据用户任务逻辑，输出一份完整、结构化的 DAG 数据（节点列表 + 边关系 JSON），不再参与后续调度；执行引擎读取这份独立 DAG 数据，自主完成全流程调度、节点分发、并行运算。

**好处：** 将 Agent 执行任务的流程固定化，DAG 图可视化后可以清楚判断任务执行逻辑是否是我们想要的，保证可见即所得。
**坏处：** 相比 PAE 框架可根据前一步结果动态改变下一步计划，本方案是固定化的。但针对节点执行失败的情况，支持三种异常处理机制确保流程完整执行。

## 四、Plan 优化闭环（plan-opt）

### 问题分析

Plan Agent 生成 DAG 可能存在的 5 类问题：
1. **任务逻辑错误** — 遗漏步骤、颠倒步骤、无效步骤
2. **DAG 逻辑错误** — 环路、孤立节点、汇聚分支混乱
3. **输出格式不正确**
4. **任务颗粒度失衡** — 节点太大或太小，影响并行度和可复用性
5. **并行度不够** — 未能充分利用 DAG 的并发能力

### 优化手段（6 层）

**① Prompt 层 — 说清楚要做什么 + 规则是什么**
- 强制输出模板 — JsonSchema 约束输出格式
- 拆解规则 — 检索/工具操作必须在生成类节点之前；独立无依赖任务拆为并行节点
- 生成规则 — 不存在循环依赖；所有边指向已定义节点；用户需求全部覆盖
- 颗粒度规则 — 单次工具调用 = 1 个节点；单一独立目标 = 独立节点

**② FewShot 样本 — 举例说明**
- 标准样本 — 基础串行流程、多并行分支、带汇聚节点复杂拓扑
- 反例样本 — 展示错误 DAG（反向依赖、环路反例）+ 修正后的正确 DAG

**③ 后置校验层 — 保证 DAG 无环 + 合法性检测**
- 环路检测、引用合法性检测、步骤完整性检测

**④ 分级 Plan（待实现）**
- 针对长任务先进行粗任务划分，再调用子 Plan 单独生成 DAG
- 避免单次生成超大图导致输出截断、逻辑混乱

**⑤ 双 Agent 评审**
- 引入评审 Agent，独立评审流程逻辑、依赖、环路、需求匹配度，输出修改意见

**⑥ 迭代数据闭环优化 — 基于 Reflexion 的自改进机制**
- **Actor → Evaluator 闭环：** 采集所有校验失败、执行失败的错误 DAG 和用户原始需求，作为 Evaluator 的负样本输入
- **Self-Reflection 错误归因：** 自动归类错误类型，提炼可复现的失败模式
- **Experience Replay 经验回放：** 将高频错误案例自动加入 FewShot 样本库
- **LLM-as-Judge 量化评估：** 低分样本自动回流至 Prompt 优化流程

### 测试维度

- **Plan 能力** — 任务分解、DAG 图构建（无环）、冗余步骤、多步连贯性、并发性
- **任务执行确定性** — 重试次数、稳定性指数
- **成本效率** — 总执行时间、Token 消耗量
- **无效 ReAct 循环占比下降**
- **故障场景流程完整执行率**

### 执行轨迹 Trace

节点分开存储天然保留了每一次执行的完整 Trace（输入、输出、工具调用、耗时、Token），可直接用于 Plan 质量的评估。结合 Reflexion 闭环中的 LLM-as-Judge，Trace 数据为低分样本回流提供了基础。

## 五、节点输入输出（node-io）

### STAR 分析

**Situation：** DAG 图中每个节点是一个独立任务，由子 Agent 执行。节点之间有明确先后依赖关系，后面的节点需要拿到前面节点的输出才能执行。

原本的做法：直接把子 Agent 的完整对话历史全部存下来，当下一个节点需要时，把整坨东西传给它。

**Task：** 需要确定每个节点的输出应该包含什么内容、以什么格式输出，让下游节点只拿到它真正需要的信息，同时控制上下文占用。

**Action：** 考虑了两种策略：

| 策略 | 描述 | 优缺点 |
|------|------|--------|
| **压缩策略**（借鉴 Claude Code） | 子 Agent 执行完后，把完整对话历史压缩成摘要再传 | 好处：不需要改子 Agent 行为；坏处：压缩本身消耗 Token，可能丢失细节 |
| **动态 Schema 格式化输出**（借鉴 Dynamic Workflow） | Plan Agent 在生成 DAG 时为每个节点生成 output_schema，子 Agent 按 schema 输出结构化结果 | 好处：从源头砍掉冗余，下游可直接通过字段名取数据 |

**选择：** 动态 Schema 格式化输出为主，压缩策略为兜底。因为更根本——不是"把脏数据洗干净再传"，而是"一开始就不产生脏数据"。

**Result：** 格式化输出砍掉了子 Agent 推理过程中 60%-80% 的冗余 Token。动态 schema 让每个节点的输出结构都是任务特定的，下游节点可以直接通过字段名取数据。两个策略叠加，节点传递的信息量可控制在原始输出的 10%-20% 左右。

## 六、双层并行执行引擎（parallel）

### 第一层 · 节点级并行 — KAHN 拓扑排序

Kahn 算法核心思路基于入度的拓扑排序。入度为 0 表示该节点没有任何前置依赖，可以直接执行。

**并行执行逻辑：** 入度为 0 的节点直接执行，每执行一个节点就将其指向的节点的入度减一，于是就会有新的可执行节点出现。将节点分为一批一批执行，实现更大程度的并行。

**环路检测：** 记录每个节点的入度，不断移除入度为 0 的节点并更新下游入度。如果执行完毕后仍有节点入度不为 0，说明存在环路。

### 第二层 · 工具级并行

除了节点任务层级的并行外，还有颗粒度为单个工具调用层面的并行，比如同时读多个文件。两者结合形成"节点级 + 工具级"双重的并行策略。

### 并行输出隔离

多线程并行场景下如果直接往 System.out 打印，不同任务的日志会交错混杂。做法：给每个执行步骤单独分配独立的 ByteArrayOutputStream 内存缓冲区，每个任务执行时全部写入自己专属的本地缓冲。等所有并行任务全部执行完毕后，再按照业务定义的步骤原始顺序，依次把每个缓冲区的内容批量刷新到标准输出。

**效果：** 经 200 项任务评估集测试，相比串行基线，并行执行时间缩短 23%。

## 七、节点级断点恢复（rollback）

### 核心设计

摒弃 LangGraph 整体状态快照，为每个节点独立持久化输入输出及状态至 MySQL。

**三张表：**
- `workflow.flow_data`（JSON 列）— 存 DAG 拓扑结构
- `execution_snapshot` — 存每个节点的输入输出和状态
- `execution_record` — 存整次执行的全局汇总

**运行时：** 数据传递纯走内存 HashMap，节点执行完顺手把快照同步写入 MySQL，但不从数据库读。

**断点恢复流程：**
1. 查询执行记录，校验归属
2. 重新解析 DAG，进行拓扑排序
3. 加载该执行记录的所有执行快照
4. 确定从哪个节点恢复开始（优先级：请求指定 > 第一个失败的节点 > 第一个未完成的节点）
5. 构建恢复状态（收集成功节点输出 + 分支选中信息）
6. 保存用户修改的变量
7. 更新执行记录状态为"运行中"
8. 从恢复状态开始执行

### 与 LangGraph 对比

| 维度 | DAG 图方式 | LangGraph |
|------|-----------|-----------|
| **存储开销** | 只需记录每个节点的输入输出和状态，效率高 | 每次保存完整全局状态快照，存储开销大 |
| **恢复灵活性** | 可精确指定从任意节点开始，恢复前可手动修改节点输出 | 只能从最近 checkpoint 继续，无法跳过或修改中间节点 |
| **调试粒度** | 清晰看到每个节点的执行历史和输入输出 | 只能看到完整状态，单节点调试不方便 |
| **实现复杂度** | 需设计多张表、处理节点依赖，实现复杂 | 框架自动维护状态和 checkpoint，实现简单 |
| **状态一致性** | 手动构建恢复状态时易出错 | 每次保存完整快照，恢复时直接加载 |
| **动态结构支持** | 拓扑预定义，动态分支和循环处理困难 | 整体快照天然支持循环、动态分支等复杂结构 |

## 八、Sub Agent 分发执行与 Token 优化（sub-agent）

### Sub Agent 分类与职责

| 角色 | 职责 | 绑定工具 |
|------|------|----------|
| 调研 Agent | 搜索与信息收集 | 搜索类工具（WebSearch、文件读取） |
| 审查 Agent | 代码审查与安全扫描 | 代码检查类工具、安全漏洞扫描规则 |
| 执行 Agent | 执行命令、写文件、生成报告 | 执行命令和文件写入类工具 |

### Token 消耗对比

| 方案 | System Prompt 大小 | 单次调用 | 完整 3 步任务 |
|------|-------------------|----------|---------------|
| 单 Agent ReAct | ~9K（含全部工具、策略、记忆） | 9K | 69K |
| Sub Agent 方案 | ~3K（只含当前角色规则和工具） | 3K | 41K |
| **降低比例** | | **↓67%** | **↓41%** |

Sub Agent 只加载自己角色需要的 System Prompt 和工具描述，不加载全局规则和其他角色的工具。节点结束后重置，历史不跨节点累积。

## 九、三级异常治理与条件分支路由（exception）

### 三级异常治理

基于模板方法抽象通用执行基类，自上而下封装：

```
execute（重试）
  └── doExecuteWithTimeout（超时）
        └── doExecute（异常处理）
```

**顶层 · execute（重试）：** 总入口。需要重试时通过循环调用 doExecuteWithTimeout，无需重试则直接执行。重试间隔支持**固定、线性、指数退避**三种策略。

**中层 · doExecuteWithTimeout（超时）：** 通过 AsyncUtil 工具类将节点执行放入限时任务中，到达设定时间直接抛出超时异常。

**底层 · doExecute（异常处理）：** 捕获所有异常后统一包装，按配置分三种处理方式：

| 处理方式 | 适用场景 |
|----------|----------|
| ① 直接中断 | 关键节点失败后整体进入失败状态。适用于支付、扣款、核心写操作等 |
| ② 错误码策略 | 按预配置的错误码或默认值继续执行。适用于辅助查询、非核心推荐等 |
| ③ 失败条件分支策略 | 引导到异常处理分支，用于告警、补偿、回滚或特定兜底逻辑 |

### 条件分支路由

Plan Agent 可生成多个分支备选 DAG，执行时根据节点输出选择对应分支。实现方式：在每条边上加 **condition** 字段——节点执行完成后，只有匹配条件的边被"激活"，仅减少激活路径上节点的入度。

未选中分支的节点永远不会入度为 0，自然不会被调度执行。通过这种**级联裁剪**策略，可以在不修改 KAHN 调度器的情况下原生支持分支与选择。

## 十一、面试 Q&A 话术

### Q1：为什么做这个项目？

**回答：** 日常使用 Agent 时发现，我已经给了非常明确的指令，但它就是会跳过或拒绝执行。比如让它先检索竞品资料再生成分析报告，结果它根本没去检索，因为它觉得自己知道。这个问题的本质是 Agent 会无视你的指令和规划，自己决定怎么做。

我调研了两种方式：Workflow 是限定整个流程，Hooks 是约束某一步前后要做什么。我的需求属于前者，就选择了 Workflow 路径。

一般的 Workflow 是由人来定义的，但联想到 Plan and Execute 的架构，由 AI 来 plan，于是我就想到把 DAG 图的构建交给大模型来完成。核心思想就是：Plan Agent 构建 DAG 图，将 DAG 图可视化展示给用户确认，再用执行引擎读取 DAG 图自动完成任务，确保规划了就一定会执行。

### Q2：DAG 图怎么保证正确性？

**回答：** 主要三个策略：第一，给他说清楚要做什么（Prompt 约束，JsonSchema 输出模板）；第二，列举清楚规则是什么（拆解规则、生成规则、颗粒度规则）；第三，举一些例子（FewShot 标准样本 + 反例样本）。这是 Prompt Engineering 里最基本的操作。

然后我设置了一个后置校验层（环路检测、步骤完整性检测、引用合法性检测）。Prompt + 样本 + 校验做到位了，DAG 质量有了基本保障。

但模型会犯错，而且同样的错误可能反复出现。所以我参考了 Reflexion 的思路，把每次执行失败的 DAG 当作负样本收集起来，自动分析失败原因，再把高频错误注入到 Prompt 和样本中。这样每次失败都变成一次教学，Plan 能力就随着使用次数越来越多，形成一个持续改进的闭环。

### Q3：节点间信息传递怎么做的？

**回答：** 我采用了动态 Schema + 压缩兜底的双层策略。主方案是让 Plan Agent 在生成 DAG 时为每个节点定义 output_schema，子 Agent 按 schema 输出结构化结果，下游节点可以直接通过字段名取数据。对于不适合结构化输出的节点，用压缩策略做兜底，用便宜的模型把完整对话历史压缩成摘要再传递。两种策略叠加，节点传递的信息量可以控制在原始输出的 10% 到 20% 左右。

### Q4：为什么用 Sub Agent 而不是单 Agent？

**回答：** 我分析过 Token 的构成占比，发现工具定义和 System Prompt 占了超过一半，是消耗最大的一块。单 Agent ReAct 一次调用需要加载所有工具的 Schema 和完整指令，大概 9K；但 Sub Agent 只需要加载自己相关的工具定义和角色指令，大概 3K 就够了。所以把职责拆开之后，每类 Agent 只关心自己该做的事，Token 消耗自然就降下来了。

目前我设定了三类 Sub Agent：调研、审查和执行。这么设计是因为我觉得 Agent 应该匹配到某一个领域里面才好设计，也就是说是交给使用者去定制的。比如写代码的场景，执行 Agent 的内容就会针对代码场景做针对性的修改。

### Q5：异常处理和分支路由怎么实现的？

**回答：** 因为这里是固定的 DAG 图，如果没有异常治理和条件分支路由，就会出现执行结果不如预期、流程进行不下去的情况。

我设计了三级异常治理：顶层是重试策略（固定/线性/指数退避），中层是超时控制，底层是异常处理。异常处理又分三种方式：直接中断（适用于支付、扣款等关键节点）、错误码策略（标记失败但继续执行）、失败条件分支（引导到异常处理路径）。

条件分支路由是为了解决 Plan Agent 不知道这一步结果是什么，遇到不同结果可能有不同路径的问题。我在每条边上加 condition 字段，只有匹配条件的边才会被激活。通过这种级联裁剪策略，不用修改 KAHN 调度器就能原生支持分支。

### Q6：和 LangGraph 相比有什么优势？

**回答：** 最大的优势是 DAG 图的可视化和可干预性。用户可以清楚看到整个执行计划，知道每一步在做什么。断点恢复方面，LangGraph 用的是整体状态快照，存储开销大，恢复只能从最近 checkpoint 继续。我的方案是逐节点存储，存储效率高，可以精确指定从任意节点开始恢复，恢复前还能手动修改节点输出。并行执行方面，DAG 图天然支持更好的并行策略，能实现"节点级 + 工具级"双层并行。

### Q7：测评结果怎么样？

**回答：** 我设计了 200 个任务的测评集，覆盖常规流程、并行分支、复杂拓扑、边界样本和对抗样本。DAG 构建正确率 97%，子 Agent 任务完成率 94%，并行执行时间缩短 23%，Token 消耗降低 14%。关于测评方法论的详细说明，参考《Agent 测评思路》文章。
