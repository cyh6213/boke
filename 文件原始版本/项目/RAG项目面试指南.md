## 一、项目概述

**项目名称：** 企业知识库 Agentic RAG

**项目定位：** 面向企业内部的知识库问答系统，具备完整的检索增强生成（RAG）全链路能力，从文档上传、分片处理、混合检索、智能路由到生成优化，并提供 MCP Server 能力供外部 Agent 生态接入。

**核心亮点：**
1. 全链路召回率优化（从 68.4% 提升至 81.2%）
2. 幻觉率优化（忠实度从 0.72 提升至 0.96）
3. 智能路由（三层决策机制，8 种查询类型策略分发）
4. MCP Server 接入（外部 Agent 可通过标准化协议查询知识库）

---

## 二、项目来源（origin）

**为什么做这个项目？**

该项目主要有两个亮点：第一是针对召回率和幻觉率的优化，每一个优化过程都进行了测试，确保优化的策略是有效的。第二是智能路由，首先分离出不需要向量检索、可以直接回答的问题，在一定程度上减少耗时。其次智能路由解决的问题是针对复杂问题，提供了一些个性化的检索策略。

## 三、核心流程（flows）

### 混合检索流程

```
① 问题改写（不同问题，不同策略）
  │
  ▼
② 向量化（BGE-m3 embedding → dense 向量）
  │
  ▼
③ 稀疏向量化（BGE-m3 → sparse 向量，替代传统 BM25）
  │
  ▼
④ 向量搜索 dense（Milvus HNSW 索引，余弦相似度，k*30=300 篇）
  │
  ▼
⑤ 稀疏搜索 sparse（关键词级别精确匹配）
  │
  ▼
⑥ RRF 融合（倒数排序融合，得出排名靠前的结果）
  │
  ▼
⑦ Rerank 重排（BGE-reranker-v2-m3，选取前 k 篇）
```

### 问答流程

```
① 前置决策
   ├── 提示词防护（拦截 Prompt 注入、越狱攻击、敏感指令）
   └── 敏感数据脱敏（手机号/身份证/银行卡自动掩码替换）
  │
  ▼
② 分类路由
   ├── 简单问题：省略向量查询，提升响应速度
   └── 多跳/复杂问题：在检索策略、改写深度、上下文组装方式、生成策略四个维度针对性优化
  │
  ▼
③ 检索拒答（检索结果评分未达阈值则直接回复无资料，降低幻觉）
  │
  ▼
④ 生成审核（RAGAS 校验回答忠实性，判定是否需要多轮迭代补全重生成）
```

## 四、召回率优化（recall-opt）

### 全链路优化策略

| 阶段 | 策略 | 效果 |
|------|------|------|
| 上传阶段 | 两级四层语义分块策略 | 保证语义完整性 |
| 检索阶段 | 问题改写 + 双路召回（稠密向量 + 稀疏向量） | 双路召回 +8.28pp |
| 排序阶段 | RRF 融合策略 + ReRank 重排 | Rerank 再 +4.20pp |

### 双路召回对比

纯 dense 基线 68.38% → 稠密 + sparse 双路 76.66%，提升 **+8.28pp**。稀疏向量替代 BM25 后额外贡献 **+1.00pp**。

### 消融实验：recall_cap@5 逐级提升

| 方案 | recall_cap@5 | 较上一步提升 |
|------|-------------|-------------|
| bm25 纯关键词（参照） | 61.50% | — |
| dense 纯向量检索（基线） | 68.38% | +6.88pp |
| + BM25 双路混合（固定权重） | 75.66% | +7.28pp |
| BM25 → sparse（固定权重） | 76.66% | +1.00pp |
| + RRF 融合方式优化 | 77.0% | +0.34pp |
| + Rerank 重排（候选池 50） | **81.2%** | **+4.20pp** |

### 分片优化

**为什么分片？**
1. 向量模型有长度限制
2. 长文本语义太杂、检索不准
3. 丢给大模型回答时，依然有窗口限制

**两级四级语义分块策略：**
- **第一层 · 父块：** 流式解析，达到 parentChunkSize（1MB）自动切割，避免 OOM
- **第二层 · 子块（四级语义切割）：** 按 chunkSize 512 TOKEN 分割
  1. 优先按段落分割（\n\n）
  2. 段落过长按句子分割
  3. 句子过长按词语分割（HanLP 分词，不拆词）
  4. 最后兜底按字符分割
- **重叠分块：** 每个分块前后保持上下文冗余

**代码分片策略：** 使用 JavaParser 做 AST 分析，解析语法树，提取类和方法的起止行号。类 chunk 只提取前 5 行作为类签名，避免整个类代码全部塞进去。

### 问题改写的五种策略

| 策略 | 描述 |
|------|------|
| 简单改写 | 处理口语化查询，消除代词补充隐含信息 |
| 问题拆解 | 把多个问题拆解分开查询，对比类问题分开查询后合并 |
| HyDE | 让 LLM 生成假设答案，用答案向量去检索，语义匹配度更高 |
| 多角度扩写 | 把查询改写成 3-5 种表述分别检索后合并去重 |
| 后退提问 | 把具体问题抽象到通用原理层面，先检索背景知识再检索具体细节 |

## 五、幻觉优化（halluc-opt）

### 五重优化策略

| 优化手段 | 描述 |
|----------|------|
| ① Prompt 约束 | 让他没有的就说不知道 |
| ② 低分拒答 | 检索分数过低直接回复没有资料，不让大模型硬编 |
| ③ 结构化输出 | 让 LLM 输出结构化的结论，每个结论标注来源 |
| ④ RAGAS 核查 | 生成后调用 LLM 或 RAGAS 核查忠实性、答案相关性 |
| ⑤ 参数调低 | 降低 temperature、top-p 等参数，让回答更严谨 |

### 生成阶段忠实度消融实验

| 优化方案 | 忠实度 | 答案相关性 |
|----------|--------|-----------|
| 无优化（基线） | 0.72 | 0.65 |
| + Prompt 约束 | 0.82 | 0.70 |
| + 低分拒答 | 0.88 | 0.76 |
| + 结构化输出（标注来源） | **0.96** | **0.84** |

## 六、RAG 测评（eval）

### 测评数据来源

- **检索阶段：** 基于 C-MTEB / T2Retrieval 数据集，测试数据库为 Milvus，原始语料库约 12w 条，分块后约 36w 条，使用前 2000 条 query 测试。核心指标为 recall_cap@5（cap=5）。
- **生成阶段：** 基于 RAGAS 框架 + LLM-as-Judge 模式，对 200 条问答对自动评分。

### 检索阶段 7 项指标全面对比

| 指标 | 基线 dense | 最优方案 | 提升幅度 |
|------|-----------|----------|----------|
| recall_cap@5 | 68.4% | **81.2%** | +12.8pp |
| recall@5 | 56.5% | **67.5%** | +11.0pp |
| ndcg@5 | 71.6% | **82.1%** | +10.5pp |
| mrr@5 | 85.6% | **91.1%** | +5.5pp |
| precision@1 | 82.6% | **88.2%** | +5.6pp |
| f1@5 | 47.9% | **57.3%** | +9.4pp |
| 端到端延迟 | 55ms | **362ms** | +307ms |

### 固定权重融合 vs RRF 融合

- **无 Rerank（仅融合检索）：** fixed_sparse_dense 76.66% vs rrf_sparse_dense 77.0%，差距仅 0.34pp
- **开启 Rerank 后：** fixed 融合 + rerank 提升不足 1pp；RRF 融合 + rerank 冲到 81.2%，差距显著

### 实验配置

- 模型：BAAI/bge-m3（dense+sparse）、bge-reranker-v2-m3
- 向量库：Milvus HNSW 索引
- 融合规则：fixed 固定权重 = 0.6*dense + 0.4*sparse；RRF k=60；rerank 候选池 50 条

## 七、智能路由（router）

### 三层决策机制

| 层级 | 方式 | 功能 |
|------|------|------|
| 第一层 · 规则引擎 | 关键词和正则匹配 | 快速过滤闲聊、纯计算类问题 |
| 第二层 · 语义分类器 | Spring AI Alibaba QuestionClassifierNode | 从 4 个正交维度独立判定 |
| 第三层 · 实体关系检测 | 提取实体数量和关系复杂度 | 超过阈值自动判定为多跳查询 |

### 语义分类器 4 个正交维度

| 维度 | 取值 |
|------|------|
| 检索模式 | 无需检索 / 单次检索 / 双池独立 / 多轮补充 / 多跳 ReAct 链 |
| 时间要求 | 无 / 指定时间或最新 |
| 生成格式 | 事实陈述 / 分步骤 / 对比表格 / 列表汇总 / 推理链 / 声明比对 |
| 验证标记 | 否 / 是 |

### 8 种查询类型处理策略

| 类型 | 处理策略 |
|------|----------|
| 无需检索 | 规则引擎第一层拦截，跳过向量检索，直接返回模型回答或预设回复 |
| 单跳事实查询 | 高阈值（0.75）精确召回 1-3 个片段，聚焦关键词提取和指代消除 |
| 对比查询 | 两次独立检索分别放入 A 池和 B 池，禁止用模型知识填补空白 |
| 技术操作查询 | 提取操作关键词改写查询，优先命中有步骤编号/代码块的文档 |
| 时序与时效性查询 | 注入时间参数，按时间范围过滤或倒序排序 |
| 验证查证查询 | 先做声明抽取，转成确定性查询去检索，做声明 vs 事实比对 |
| 列举聚合查询 | 低阈值（0.6）宽召回，候选集 top-50，关键词补充检索 |
| 多跳推理查询 | 分解为子查询链，每步基于前序结论动态构建新查询 |

### 全链路延迟分解

| 环节 | 耗时 | 占比 |
|------|------|------|
| 纯向量检索 | ~55ms | ~3% |
| Rerank 重排 | ~300ms | ~18% |
| **检索管线合计** | **360ms** | **~22%** |
| LLM 推理（首 Token） | ~350ms | ~21% |
| LLM 推理（后续 Token） | ~950ms | ~57% |
| **LLM 推理合计** | **1,300ms** | **~78%** |
| **总计** | **~1,660ms** | **100%** |

**结论：** LLM 推理占 ~78%，检索管线仅占 ~22%。跳过检索只能节省约 22% 的总时间，智能路由的主要价值在于降低 API 调用成本，速度提升是附带收益。

## 八、其他亮点（other）

### 上传优化

基于 Redis Bitmap 实现并发分片上传与状态追踪，结合 RocketMQ 异步解析解耦，大文件上传响应速度提升 65%。

**流程：** 前端按 5MB 分片上传 → 后端校验文件类型，存入 MinIO，Redis Bitmap 记录进度 → 校验完整性，MinIO 合并文件 → 发送 RocketMQ 消息，异步触发文档解析、向量化、写入 ES。

**策略：**
1. **幂等设计** — 重复上传前查 Redis 标记
2. **断点续传** — 重传自动跳过已上传部分
3. **重试机制** — 单个分片上传失败，前端内置重试
4. **完整性校验** — 后端算 MD5 判断
5. **最终一致** — 定时任务核对自动修复

### 权限控制

基于 RBAC + OrgTag + Spring Security + JWT 实现多级权限控制与双令牌认证。

**双令牌机制：**
- **Access Token：** 核心通行证，有效期 1 小时
- **Refresh Token：** 长期凭证，有效期 7 天，可通过 Redis 快速吊销
- 自动刷新：当 Access Token 距离过期 < 20 分钟时访问，自动刷新令牌

**两层权限控制：**
1. 提取校验 Token，封装用户信息到 SecurityContextHolder
2. 角色级接口权限校验
3. 加载组织标签，存入请求上下文
4. 搜索时自动构建带权限条件的 ES 查询，强制只返回有权查看的数据

### MCP Server

**场景：** 公司内部员工日常使用各类 AI Agent（Cursor、Dify、Claude Desktop 等），需要访问企业私域知识。把 RAG 系统封装为 MCP Server，只负责按权限提取文档片段并返回原文，不承担回答生成。

**实现：** 基于 Spring AI Alibaba 的 MCP Server Starter，增加 `spring-ai-mcp-server-webmvc` 依赖。项目启动后自动暴露 MCP 端点，提供两个标准方法：`listTools` 和 `callTool`。

**权限：** MCP 协议本身没有认证机制，权限完全在应用层实现。通过 MCP 请求参数携带员工的 Access Token，校验 Token 有效性后走和网页端完全一致的过滤器链。

## 九、核心技术原理（principles）

### 向量检索的原理

- 长度代表内容的多少，信息量的大小
- 角度代表语义
- **余弦相似度：** 计算两个向量的夹角，夹角越小越相似。只看方向
- **欧式距离：** 计算两个向量的距离，距离越小越近
- **点积：** 计算两个向量方向一致性与长度的数值（l1*l2*cos），结果越大通常越相似。既看方向又看长度。需要归一化

### BM25 原理

ES 默认的关键词相关性算法，根据词频、文档长度计算匹配度。
- **k1：** 越大，关键词频率对匹配度影响就越大
- **b：** 越大，对长文档的惩罚就会越重

### 三种检索方式的区别

| 方式 | 描述 | 优势 |
|------|------|------|
| **稠密向量** | 把文本压缩成固定维度（如 2048 维）的浮点数向量 | 能理解语义相似度（猫 vs 狗是相似的） |
| **稀疏向量** | 超高维向量（几万到几十万维），每个维度对应具体词 | 保留关键词精确匹配能力 + 向量空间距离计算 |
| **关键词检索 BM25** | 基于词频统计的精确匹配 | 速度快、可解释性强 |

**稀疏向量是稠密向量和关键词的"中间态"：** 下接关键词的精确性（每个维度对应具体词），上接稠密向量的语义理解（可做向量空间的距离计算）。双路召回用稠密 + 稀疏搭配效果最好：稠密负责语义泛化，稀疏负责精确命中。

### RRF 重排序

在多路排序列表中，忽略不同排序方式的分数，只看排名的一种排序方式。

- **倒数打分：** 每个列表里，按位置算分 1/(k+rank)
- **分数累加：** 同一文档在所有列表中的得分求和
- **重排输出：** 按总分从高到低排序
- **k：** 平滑常数，默认 60；k 越大，得分越平均；k 越小，第一名优势越强

**好处：** 可以忽略不同排序方式的分数
**缺点：** 忽略了分数，不包含分数信息

### ReRank 原理

- **Embedding 模型（Bi-Encoder）：** 分别计算 Query 和文档的向量，然后对比相似度。好处是快、可以全库搜索。但只看到了表面的匹配，没有做深度交互。
- **Rerank 模型（Cross-Encoder）：** 把 Query 和文档拼接在一起，直接分析每个词之间的关系。能更深层次理解 Query 和文档的关系。代价：速度慢，开销大。

所以一般是先用 embedding 搜广度，再用 Rerank 精细化。

## 十、面试 Q&A 话术

### Q1：为什么做这个项目？

**回答：** 这个项目主要有两个亮点。第一点是针对召回率和幻觉率的优化，每一个优化过程都进行了测试，确保优化的策略是有效的。第二点是智能路由，首先分离出不需要向量检索、可以直接回答的问题，在一定程度上减少耗时。其次智能路由解决的问题是针对复杂问题，提供了一些个性化的检索策略。

### Q2：召回率是怎么从 68% 提升到 81% 的？

**回答：** 我做了 6 组逐级消融实验。从纯 dense 向量检索基线 68.38% 开始，第一步加 BM25 混合检索涨到 75.66%，第二步把 BM25 替换成 BGE 稀疏向量涨到 76.66%，第三步把固定权重融合改成 RRF 融合涨到 77.0%，最后加 Rerank 重排冲到 81.2%。每一步都有数据支撑。

其中有个有意思的发现：固定权重融合 + Rerank 提升不到 1pp，但 RRF + Rerank 能提升 4.2pp。原因在于 RRF 输出的排名列表比固定权重更"干净"，Rerank 模型在高质量的候选集上才能发挥效果。

### Q3：检索链路中哪些环节贡献最大？

**回答：** 最大贡献来自双路混合检索（+7.28pp），其次是 Rerank 重排（+4.20pp）。稀疏向量替代 BM25 贡献了 +1.00pp，RRF 融合方式优化贡献 +0.34pp。

### Q4：分片策略是怎么设计的？

**回答：** 我采用的是两级四层语义分块策略。第一层是父块，流式解析，达到 1MB 自动切割，避免 OOM。第二层是子块，按 512 Token 大小四级语义切割：优先按段落分割，段落过长按句子，句子过长按词语（HanLP 分词），最后兜底按字符。全程保证语义完整性，不会把完整句子、词语强行切断。另外还给每个分段加了上下文冗余，避免遗漏关键信息。

代码分片用的是 JavaParser 做 AST 分析，保持代码语义完整性，不会像按字符数分段那样切断方法或类。

### Q5：如何降低幻觉率？

**回答：** 用了五个策略。第一是 Prompt 约束，让他没有的就说不知道。第二是低分拒答，检索分数过低直接回复没有资料，不让大模型对着不相干的内容硬编。第三是结构化输出，让 LLM 输出结构化的结论，每个结论标注来源。第四是 RAGAS 核查，生成后再核查一次。第五是调低 temperature、top-p 等参数。从消融实验看，忠实度从 0.72 提升到了 0.96。

### Q6：智能路由是怎么实现的？

**回答：** 三层决策机制。第一层是规则引擎，基于关键词和正则快速过滤闲聊、计算类问题。第二层是语义分类器，用 Spring AI Alibaba 的 QuestionClassifierNode 从 4 个维度独立判定：检索模式、时间要求、生成格式、验证标记。第三层是实体关系检测，提取实体数量和关系复杂度，超阈值自动判定为多跳查询。

不过在实际场景中，简单问题分离的收益有限。因为 LLM 推理占 78% 的时间，检索管线只占 22%，跳过检索最多省 22%。而且用关键词匹配可能不精准，用 LLM 分类增加的耗时远大于减少的耗时。所以智能路由的主要价值在于降低 API 调用成本，速度提升是附带收益。

### Q7：多跳推理是怎么实现的？

**回答：** 针对复杂问题，我把它分解为子查询链，每步基于前序结论动态构建新查询。比如"程愚瀚和鲁迅的关系"——先查程愚瀚是电子科大学生，再查电子科大的人才，然后关联到鲁迅。这个策略弥补了向量 RAG 在全局性问题和多跳推理等需要逻辑链条的复杂问题上的短板。

### Q8：为什么做 MCP Server？

**回答：** 公司内部员工日常使用各类 AI Agent 完成工作，这些 Agent 需要访问企业私域知识，但不可能让每个员工都打开 RAG 系统手动查询。同时，本系统的问答接口消耗 Token，更适合作为"资料提取层"而非回答层。

所以我把 RAG 系统封装为 MCP Server，只负责按权限提取文档片段并返回原文，不承担回答生成。员工的外部 Agent 拿到原文后自行组装回答。这样既节省了 Token 开销，又让知识库能力被任意 Agent 生态复用。

实现上基于 Spring AI Alibaba 的 MCP Server Starter，增加一个依赖即可。权限通过 MCP 请求参数携带 Access Token，在应用层完成校验。

### Q9：权限控制怎么做的？

**回答：** 基于 RBAC + OrgTag + Spring Security + JWT 实现。双令牌认证：Access Token 有效期 1 小时，Refresh Token 有效期 7 天。两层权限控制：角色控制能否进入网页，标签决定能否访问文件。搜索时自动构建带权限条件的 ES 查询，强制只返回有权查看的数据。

### Q10：上传优化怎么做的？

**回答：** 基于 Redis Bitmap 实现并发分片上传与状态追踪，结合 RocketMQ 异步解析解耦，大文件上传响应速度提升 65%。核心策略包括幂等设计、断点续传、重试机制、完整性校验、最终一致。
