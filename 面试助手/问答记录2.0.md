问题
可以讲一下你对harness的理解是什么吗？
回答
关于这个问题，我认为可以从定义和我们项目的实践两个方面来看。

第一，Harness 的定义。 Harness 这个概念本质上是在回答一个问题：为什么同样一个模型，在不同的产品里表现天差地别？答案就是 Agent 等于模型加 Harness，模型提供的是智能引擎，而 Harness 是让这份智能真正落地的那套系统。一个裸模型本质上只是一个文本输入输出的函数，它记不住上下文、执行不了代码、访问不了实时数据。Harness 就是围绕这个函数搭建的一整套基础设施，包括文件系统让它能持久化存储、沙箱让它能安全执行代码、记忆系统让它能跨会话学习、压缩机制防止它在长任务中性能衰减。这些东西的设计原则是从期望的 Agent 行为逆向推导的，你想要 Agent 能做什么，就在 Harness 里给它搭什么能力。所以 Harness Engineering 本质上是一种系统工程思维，它承认模型的智能是不完美的，但通过设计好的环境、工具和反馈循环，可以让任何模型在特定任务上发挥出远超其本身的能力。

第二，我们项目的实践。 在我的 Workflow 项目中，我把 Harness 当成一轮任务执行的业务外壳。如果把这些逻辑都塞在 Plan Agent 或者调用方里，DAG 校验、AI 推理、数据库、Trace 记录和状态管理会混在一起，后面换 Plan 模型或改执行策略都会很难维护。调用方只负责发起请求和执行结果接收，Plan Agent 只负责 DAG 生成，Sub Agent 只负责单个节点的执行，而 Harness 统一负责 DAG 校验、拓扑解析、Sub Agent 分发与上下文构建、状态持久化和 Trace 记录。好处有三点：把不稳定的模型行为和确定的执行逻辑分开、让每一层职责单一、可测试性。

问题
你知道怎么样去解决agent长上下文漂移的问题。
回答
关于这个问题，我认为可以从通用策略和我们项目的实践两个方面来看。

第一，通用的解决思路。 针对长上下文漂移，主要有四种常见手段：一是每轮注入原始目标，在 System Prompt 中重复任务背景，防止遗忘；二是阶段性总结，定期让模型压缩历史对话为摘要，控制 Token 并保留关键信息；三是外部监督，引入独立的检查 Agent 监控执行轨迹，发现偏离及时纠偏；四是任务分解，将长链路拆解为短任务，明确每个节点的输入输出定义，降低单点复杂度。

第二，我们项目的实践。 在我的 Workflow 项目中，我通过 DAG 图从物理架构上彻底解决了这个问题。我不依赖模型去“记”目标，而是由 Plan Agent 预先输出一张确定的 DAG 图，执行引擎严格按照图的拓扑结构调度节点。这样，Agent 在每个节点只负责单一子任务，无法跳步或发散。同时，我在节点间传递数据时，只保留上一个节点的关键输入和输出（格式化后），而不是完整的历史对话，确保下游节点的上下文始终保持在 10%-20% 的高信噪比状态，从而避免了早期目标被后续大量无关信息稀释导致的漂移。

问题
你对于上下文工程有什么经验吗？了解什么？
回答
关于上下文工程，我的经验主要集中在控制上下文污染和提升信噪比这两个核心维度。我觉得主要有a、b、c这几点：

关于a点，节点级输入输出格式化。 在我的 Workflow 项目中，最大的痛点就是下游节点的 Context Window 容易被上游的完整对话历史占满。为了解决这个问题，我摒弃了直接传递“完整对话历史”的做法，改为只提取并格式化上一个节点的关键输入和输出。这样做的目的是严格控制下游节点的上下文占用率，使其保持在 10%-20% 的高信噪比状态。这不仅节省了 Token 成本，更关键的是防止了早期目标被后续大量冗余信息稀释，从物理上切断了上下文漂移的可能。

关于b点，Sub Agent 隔离上下文边界。 长对话的核心问题是上下文污染——主 Agent 和工具交互产生的消息越来越多，关键信息被淹没。我的项目采用了 Sub Agent 机制，将复杂任务拆解后分发给不同角色的子代理。每个 Sub Agent 拥有独立的执行环境和最小权限的工具集（Skill/Tool），它们只处理特定子任务，结束后只回传摘要给主流程。这种设计不仅减少了 Token 消耗，更重要的是实现了上下文的逻辑隔离，避免了无关信息在主 Agent 中产生干扰。

关于c点，基于数据的优化验证意识。 在 RAG 项目中，我深刻认识到上下文优化不能靠直觉。例如在智能路由策略中，我原本认为某种复杂的检索路径能提供更丰富的上下文，但通过 RAGAS 测评框架和消融实验发现，它反而引入了噪声导致幻觉率上升。这让我明白，上下文工程的本质是在“信息丰富度”和“模型注意力集中度”之间找平衡，必须通过量化指标（如 Recall、Faithfulness）来验证每一次上下文构建的有效性。

第一，Scale 的定义。 在 AI Agent 领域，Scale 通常指的是通过增加资源（如算力、数据量）或扩大规模（如并发量、任务复杂度）来提升系统能力或吞吐量的过程。对于后端系统而言，Scale 往往涉及水平扩展（Horizontal Scaling）以应对高并发，以及垂直扩展（Vertical Scaling）以提升单点性能。核心挑战在于如何在扩展过程中保持系统的稳定性、一致性和成本可控性。

问题
在你优化你这个plan agent，它生成DAG图的这个过程中，你针对那些bad case，有没有什么就是怎么处理这些bad case，你有没有什么心得。
回答
针对 Plan Agent 生成 DAG 图过程中的 Bad Case，我的处理心得主要围绕“事前约束、事后校验、闭环回流”这三个阶段展开。

第一是事前把规则喂给模型。 一开始直接让模型生成 DAG，容易出现跳步、环路或者节点颗粒度不稳定（有的太大没法并行，有的太小开销过大）。所以我做了两件事：一是用 JsonSchema 强制约束输出格式，并制定严格的拆解规则，比如“检索/工具操作必须在生成类节点之前”、“独立无依赖的任务拆成并行节点”；二是引入 FewShot 样本，不仅提供标准样本，还特意加入反例样本——展示错误的环路或反向依赖的 DAG，让模型明确知道“什么是不对的”。

第二是设置后置校验层。 Prompt 和样本只能保证大概率正确，但模型还是会犯错。所以我加了一个后置校验层，专门做环路检测、步骤完整性检测和引用合法性检测。如果校验不通过，直接拦截，防止错误的 DAG 进入执行引擎导致任务失败。

第三是建立数据闭环回流。 这是我觉得最重要的一点。之前的方案只是单次拦截，同样的错误可能反复出现。于是参考了 Reflexion 的思路，我把每次校验失败或执行失败的 DAG 当作负样本收集起来，自动分析失败原因（是逻辑错误还是格式错误），再把高频错误案例注入到 Prompt 和 FewShot 样本中。这样每次失败都变成一次教学，Plan 的能力就随着使用次数越来越多，形成一个持续改进的闭环。

问题
我看你在简历上写，你对于SDD规范驱动开发，然后web coding有一些相关的经验。那你的经验是什么？
回答
关于这个问题，我认为可以从定义和我们项目的实践两个方面来看。

第一，SDD 的定义。 规范驱动开发（Spec-Driven Development），也就是先写规格文档——包括需求分析、技术方案、各种 rule——然后再生成代码的开发模式。其实想一下也知道，我们想让人完成一个项目需要什么，那让 agent 完成一个项目也就需要什么。如果像 vibe coding 一样，只告诉它一个很模糊的需求，那就很难得到你想要的结果。

第二，我们项目的实践。 我的经验主要经历了从“依赖 Skill”到“流程内化”的三个阶段：

首先是初始化项目格式。 我系统性地学习了大厂的经验，明确了不只是代码文件怎么组织，还包括文档文件放在哪——比如需求文档、修改记录、技术方案等。这些不属于代码的文档应该划分为两部分：一部分是所有项目共享的 rule 和模板（如基础层代码格式、模块层架构规范）；另一部分是和项目内容有关的，比如变更记录。把这些详细的记录落到文件，会极大地增强我对代码的自信心和了解程度。

其次是建立规则体系。 我把编码规范、架构约束、开发流程写进 rules 文件。通过 rules 文件要求 AI 在编码前先读取所有相关文档，严格按照文档内容来实现。这解决了之前 Vibe Coding 时代“跟开盲盒一样，不清楚哪一个类是干什么的”的问题。

最后是让 AI 按文档执行。 我不再依赖某个具体的 Skill 来管理流程，而是把规范驱动开发的流程内化到了自己的大脑里。我知道什么时候该写文档、什么时候该生成代码。这种“先写文档，再让 AI 按照文档去执行”的模式，让我能够更系统地控制开发质量，而不是单纯地堆砌技术点。

第一，Workflow 项目的优点。 我的项目最核心的价值是通过 DAG 图强制 Agent 按既定流程执行，解决了跳步和遗漏的问题。Agent 想跳过检索直接生成答案？不行，因为 DAG 里没有那条边。同时 Harness 系统把不稳定的模型行为和确定的执行逻辑分开，让每一层职责单一。调用方只负责发起请求，Plan Agent 只负责 DAG 生成，Sub Agent 只负责单个节点执行，Harness 统一负责校验、调度、状态持久化和 Trace 记录，也让系统有了可测试性。此外，双层并行执行系统通过 DAG 的入度计算实现节点级并行，入度为 0 的节点同时执行；第二层是在 Sub Agent 内部支持同格式调用多个工具，实现更细粒度的并行。两层叠加让长链路任务的执行效率明显提升。

第二，Workflow 项目的缺点。 做这个项目最大的坏处是，我的想法、策略不一定是有用的，所以项目做到最后可能会发现别人的策略更好？但是能经历这个过程，能讲清楚认识也是比较好的。另外，为什么别人都写哪些项目，可能原因是哪些项目包含了面试官需要的技术栈，而我的项目可能就没有。还有，我的内心会保持怀疑，在没有成功找到实习之前，我都不知道自己的做的到底对不对，缺少肯定。
